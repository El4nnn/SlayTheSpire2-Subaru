# 规范 · 修改与记录（塔2mod）

> 📌 **canon** ｜ 最后核对：2026-11-23 ｜ 改文档的规则（12 节 + 提交前 9 条清单）

> 生效：2026-11-23　｜　适用范围：`docs\`、根目录 `*.md`、`docs\知识库\`、笔记（notes）
> 这份规则是**执行标准**，不是建议。违反它的文档在 `登记表.md` 里会被标成不可引用。

---

## §0 三条总原则

| # | 原则 | 含义 | 反面 |
|---|---|---|---|
| 1 | **单一权威** | 每个主题只有一份 canon 文档；其他文档只能**指过去**，不能各写一份数字 | `cutin_工作流` §13 与 `cutin.json` 各说各的数量 |
| 2 | **证据落地** | 结论必须能落到 `文件:行` / IL 方法 / hook 相位 / 状态的唯一写入方之一 | 「已修复」「已优化」不算记录 |
| 3 | **不删只标** | 被推翻的内容不删除、不改写原文，加**勘误块**并指向替代者 | 直接改掉旧结论 → 失去追溯能力 |
| 4 | **以现版本为准**（2026-11-23 用户定） | 旧设计稿 / 旧数值与当前代码冲突时，**一律按现版本记录**，不追溯「本来该是什么」、不当成 bug 去补 | 拿 11-08 的 17 张腐蚀去反推「漏挂了 4 张」 |

> 原则 4 的边界：它**不**用来掩盖真 bug。「现版本行为与**当前设计意图**不符」照旧是 bug；
> 被它排除的是「旧文档写的样子 vs 现在代码的样子」这类**版本漂移**。

## §1 文档状态与头部标记（强制）

每篇 `docs\*.md` 与根目录 `*.md` 的**第一行标题下**必须有一行状态：

```
> 📌 **canon** ｜ 最后核对：2026-11-23 ｜ 一句话说明
```

| 状态 | 含义 | 谁可以引用它的数字 |
|---|---|---|
| `canon` | 现行权威，与代码同源 | ✅ 直接引用 |
| `active` | 仍有效，但非该主题唯一来源 | ✅ 需交叉核对 |
| `部分过期` | 主体有效，某几处已被勘误 | ⚠️ 只看勘误块指向的新结论 |
| `historical` | 只证明「当时是那样」 | ❌ 不作判据 |
| `superseded` | 已被替代 | ❌ 只作追溯 |
| `draft` | 设计稿 / 未实装 | ❌ 不当作现状 |
| `reference` | 素材 / 参考 | ❌ 数字不可引用 |
| `deprecated` | 整篇退出使用 | ❌ |

**流转**：`draft → active → canon →（被取代）→ superseded → historical`。
降级只允许「加标记」，不允许删文件（见 §9）。

## §2 什么时候**必须**写记录

命中任一条就必须当天落一条，不得留到下次：

1. **出了 bug 并定位到根因**（哪怕早已修好，只要根因是新结论）；
2. **用户否掉一版**（构图、数值、演出、文案）——记「为什么被否」，否则下一轮会重犯；
3. **数值定案**（伤害/层数/概率/时长/像素）且以后可能被问到；
4. **发现了文档与代码不一致**（登记到 `登记表.md` §6，并把权威结论写进 canon）；
5. **发版**（见 §10）；
6. **机制/流程的新硬规则**（例如「任何移除瘴气必须开 `MiasmaGuard.Allow()`」）。

不需要写：纯探索（没结论）、一次性脚本、随手改错别字、聊天里的猜测。

## §3 一条记录的必填结构

按顺序，五段，缺一段就是没记完：

```markdown
## N. <现象关键词>（用户原话优先）

**现象**：用户看到什么。原话用「」引起来。
**根因**：谁写的、写在哪个相位、为什么不是别处 → 必须带 `文件:行` / IL / hook 名。
**定论**：改在哪、为什么不用别的改法；被否掉的方案也写一句。
**验收点**：看哪行日志 / 哪个数值 / 哪张静帧。
**证据**：命令、日志片段、IL 输出（可折叠）。
```

分类型补充要求：

| 类型 | 额外必填 |
|---|---|
| 根因条目（L2） | 上面五段全要；标题带现象关键词，方便 grep |
| 过程记录（L3） | 做了哪几件、发了哪版（指纹）、**未发版清单**、**下一步** |
| 决策记录（ADR） | 背景 / 选项（≥2）/ 决定 / 代价 / 谁拍的（用户原话） |
| 素材台账 | 文件名、入出点、尺寸、依据（`blackdetect`/`scdet` 结果） |

## §4 证据等级与措辞

| 等级 | 证据 | 允许的措辞 |
|---|---|---|
| E3 | 代码 `文件:行`、`IlDump` 反编译、hook 相位顺序 | 「根因是…」「这是唯一的写入方」 |
| E2 | 游戏日志（`[Subaru]` 行）、实测数值 | 「日志显示走了 X 分支」 |
| E1 | 用户口述、截图观感 | 「用户反馈…」 |
| E0 | 推测 | 「怀疑…，**还没查到底**」 |

**硬性要求**：
- 只有 E2 及以下时，结论里必须写「**还没查到底**」，不许拿补丁当结论；
- 写「已修复」必须同时给 E3 或「用户实机确认」；
- 日志只回答三件事：**走了哪个分支 / 值是多少 / 补丁挂没挂上**——不许由日志反推「该在哪加补丁」。

## §5 数字纪律

1. **唯一来源**：`知识库\基准数字.md`。任何文档写版本号、md5、条数、机制数值，先看它；
2. **写前跑命令**，并把命令写在该数字旁边（或同节代码块）；
3. **禁止口头计数**（「大概 30 个」）——`grep`/脚本数一遍，写实测值；
4. **口径写清**：写「30 条 / 30 张 / 34 处引用」而不是只写「30」；
5. 发现新数字与基准不符：先改 `基准数字.md`（带命令），再改引用它的文档，**顺序不能反**。

## §6 改已有文档的三种动作（只能选一种）

| 动作 | 什么时候用 | 格式 |
|---|---|---|
| **A 就地修正** | 写错了 / 过期的事实（路径、版本号、条数、状态） | 直接改那几行；若改动影响结论，在句尾加 `（2026-11-23 更正）` |
| **B 加勘误块** | **结论被推翻**（做法、规则、口径变了） | 紧跟 H1 下方插入 `> **⚠️ 状态：…（日期 勘误）**` + 新结论表 + 「以代码为准」的判据；**原文保留**，不划掉整段 |
| **C 新建条目** | 新问题 / 新结论，与旧文无直接冲突 | 在**当日** L2/L3 文档里新增一节；没有当日文档就新建 |

**禁止**：
- 改别人的结论时不留日期与理由；
- 用「已更新」代替说明（必须写**改了什么**）；
- 在 `reference` / `historical` 文档里改数字（会制造第二个「权威」）——应改 canon 并加勘误块指过去。

## §7 冲突裁决流程（五步）

```
0. 分类    → 先判性质：①「文档过期 / 版本漂移」→ 按原则 4 直接记现版本，不当 bug 处理；
              ②「现版本行为与设计意图不符」→ 才是 bug，走下面的流程
1. 登记    → 登记表.md §6 加一行（冲突是什么、谁发现的）
2. 定死    → 用代码/IL 得出唯一真值（不是投票、不是「上次是这么写的」）
3. 写权威  → 基准数字.md 或对应 canon 文档写入真值 + 证据
4. 加勘误  → 旧文档加勘误块，指向 3 的结论
5. 收口    → 登记表.md 把该行标 ✅ 并写日期（设计定案也标 ✅，备注「不补代码」）
```
**禁止**：两边都改一半、或只在对话里说「以代码为准」而不落文档。

## §8 归档

- **不移动文件、不改文件名**（全仓文档与笔记里有大量 `docs\xxx.md` 路径引用，一动就断）；
- 归档 = 改状态为 `superseded`/`historical` + 在头部写「替代者是谁」；
- 目录层面只有两种情况允许搬迁：① 用户明确要求；② 一次性把**所有**引用一起改（并跑一遍 grep 验证 0 断链）；
- 三层结构参考：索引（L0）→ 专题（L1/L2）→ 笔记速查（notes）。

## §9 与发版的联动（「同步更新」时四处必改）

| 顺序 | 改什么 | 判据 |
|---|---|---|
| 1 | `知识库\基准数字.md` §1 | 版本、线上/本地 md5、上传时间 |
| 2 | `索引_文档与笔记.md` §4 | 当前工坊版本 + 本地未发状态 |
| 3 | 当日 `交接_<日期>_<主题>.md` | 改了什么、验收、未发清单清空 |
| 4 | `知识库\登记表.md` | 状态流转 + 冲突表收口 + 最后核对日期 |

发版说明本身按 `release\workshop\Subaru\更新流程.txt`：官方口吻、一条一件、≤8 条、三语对应、代码块贴出。

## §10 命名与目录

| 内容 | 位置与命名 |
|---|---|
| 根因条目 | `docs\交接_技术问题_<YYYY-MM-DD>.md`（同日可续写，一条一节） |
| 过程记录 | `docs\交接_<YYYY-MM-DD>_<主题>.md` |
| 操作手册 | `docs\<主题>_工作流.md`（如 `cutin_工作流.md`） |
| 设计稿 | `docs\<主题>_设计.md` |
| 参考 | `docs\参考_<主题>.md` |
| 结构/规则 | `docs\知识库\`（只放结构类，不放专题内容） |
| 拍板记录 | 优先写进对应的根因/过程文档的「决定」段，不单独建 ADR 文件 |

新文档建立后**当天**：加状态行 → 登记表加一行 → 索引对应分区登记。
