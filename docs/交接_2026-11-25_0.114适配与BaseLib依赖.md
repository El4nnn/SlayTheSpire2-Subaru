## 2. 本轮已改（全部未发版）

仓库当前 `dist` 是「0.3.39 + 本轮修复」，`content` 是「已上传待审的 0.3.39」，两者**故意不一致**。

### 2.1 剃刀牙 / 死归：卡面未升级、数值却是升级后（玩家反馈）

根因：`Rewind\BattleSnapshot.cs` 的 `RestoreCardStates()` 直接写 `card.CurrentUpgradeLevel`。该 setter 的 IL 只做 `AssertMutable` → 检查 `MaxUpgradeLevel` → `stfld _currentUpgradeLevel`，**不重算 `DynamicVars`、不触发 `Upgraded`**。剃刀牙（原版 `RazorTooth`，`AfterCardPlayed` → `Upgrade(1)`）的升级发生在存档点之后，死归把等级写回 0 → 面板未强化、数值仍是强化后的。

修法：
- 新增 `Extensions\CardUpgradeSync.cs`
  - `SetLevel(card, target)`：降级走 `CardCmd.Downgrade(card)`（内部会按 canonical 重建 DynamicVars/关键词/费用再逐级升回），升级走 `CardCmd.Upgrade(card, CardPreviewStyle.None)`（自带 `FinalizeUpgradeInternal`）。
  - `UpgradeNow(card, levels)`：替代旧的 `card.UpgradeInternal()`。
- `RestoreCardStates()` 顺序改为 **等级 → 关键词 → 本场费用覆盖**（降级会 `ResetForDowngrade()` 重置费用，必须最后补 `ApplyCombatCostOverride`）。
- `Rebuild()`（回档时重建已消失的牌）改用 `SetLevel`，顺带支持多级强化。

### 2.2 去内部方法依赖（15 处）

全仓 `card.UpgradeInternal()` → `Extensions.CardUpgradeSync.UpgradeNow(card)`，涉及：`BeatriceContract`、`BookOfTheDead`、`CreateCards`、`ElMinya`、`OtogiCard`、`SubaruCard`、`ToddFang`、`BeatricePower`、`CorrosionPowers`、`GreedAndSlothPowers`、`LolimancerPower`(×2)、`SphinxPower`、`VincentPower`、`PlayedPowerCards`。

### 2.3 同批未发版的其它修复（都在这份 dist 里）

| 文件 | 内容 |

| `Powers\BallroyShotPower.cs` | 演出后复查目标存活；伤害结算 try/catch（外部 mod 的伤害补丁抛异常不再打断 `Hook.AfterPlayerTurnStart`） |

## 4. API 兼容性清单（决定能不能上 0.114）

工具：`_tools\tmp\RefCheck\`（临时目录；源码 `Program.cs`，读某 dll 的 MemberRef 表，逐条对目标 `sts2.dll` 校验「成员是否存在 + 参数个数是否一致」）。
**注意**：早期版本把「返回值参数行」算进参数个数，报了 8 处假阳性；已改成从签名 blob 读，下面结果都是修正后的。

| 被检对象 | 对 0.114.0 的结果 |

| **我们的 `Subaru.dll`** | **0 missing / 0 arity → API-clean ✅** |

## 5. 未决：要不要「不依赖 BaseLib 重做」

### 5.1 现状用量（`Select-String` 实测，258 个 cs 中 41 个 `using BaseLib`）

| BaseLib 东西 | 次数 | 说明 |
|---|---|---|
| `BaseLib.Abstracts.CustomPowerModel` | 38 | 所有能力类的基类 |
| `BaseLib.Abstracts.CustomCardModel` | 2 处直接写 | 但 `Cards\SubaruCard.cs` 继承它，**全部 119 张卡**都间接依赖 |
| `CustomRelicModel` / `CustomPotionModel` / `CustomCharacterModel` / `CustomCardPoolModel` | 各 1 | 遗物 / 药水 / 角色 / 卡池 |
| `BaseLib.Extensions`（图片路径 `PowerImagePath()` 等） | 4 | 卡面/能力图标路径 |
| `BaseLib.Utils`（设置、节点工厂） | 3 | 设置页 + `CustomEnergyCounter` 等 |
| `BaseLib.Patches.Content.PrefixIdPatch` | 框架内部 | **给 `Id.Entry` 加 `SUBARU-` 前缀**，我们 589 条 loc key 全按这个前缀写 |

### 5.2 迁移的真实成本（不是换个 using 那么简单）

1. **id 与前缀语义会变**：我们的 loc key（`SUBARU-XXX.title`）和**存档里的 ModelId**（`CARD.SUBARU-…`）都建立在 BaseLib 的前缀规则上；RitsuLib 走的是它自己的 public-entry 规则。换框架 ⇒ 旧存档里的卡/遗物可能解析不到 ⇒ 必须写兼容层或放弃存档。
2. **注册方式不同**：卡池/角色/遗物/药水/自定义关键词在 BaseLib 是特性 + `Custom*Model`，RitsuLib 是 `Content.ModContentRegistry` / `CardPools` / `Scaffolding.*`，要逐项对照语义（RitsuLib 有完整对应物，但不是 1:1）。
3. **设置页**：现在走 BaseLib 的 ModConfig；RitsuLib 有自己的 Settings 程序集。
4. 迁移面大致是：**1 个卡牌基类 + 38 个能力类 + 池/角色/遗物/药水各 1 + 4 处图片路径扩展 + 3 处工具类 + 设置页**，外加 loc key / 存档兼容方案。

### 5.3 三条路线的取舍

| 路线 | 做法 | 代价 / 风险 |
|---|---|---|
| **A 等 BaseLib（推荐）** | 什么都不改，等作者发 0.114 版 | 唯一风险是作者拖延；我们自己的代码已 0.114-clean |
| **B 给 BaseLib 打补丁** | ❌ 不可行 | 缺方法是**加载期绑定失败**，Harmony 只能在方法存在时改行为；fork 一份 `BaseLib` 会与官方同 id 冲突 |
| **C 真迁移到 RitsuLib-only** | 按 §5.2 重做模型层 | 工作量最大、**存档兼容风险高**；若做，应开独立分支 + 独立版本号 + 先写迁移 ADR |
