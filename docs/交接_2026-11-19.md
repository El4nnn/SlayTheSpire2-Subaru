## 2. 标准流程（改完 → 发布）

```powershell
# 带 openpyxl 的 python（_tools\python\python.exe 不存在）
$py = "C:\Users\Elan\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\python\python.exe"

$env:TEMP = (Resolve-Path "_tools\tmp").Path; $env:TMP = $env:TEMP
$env:NUGET_PACKAGES = (Resolve-Path "_tools\nuget-packages").Path
$env:NUGET_HTTP_CACHE_PATH = (Resolve-Path "_tools\nuget-http").Path

# 1) 编译（快，先验证）
_tools\dotnet\dotnet.exe build src\Subaru\Subaru.csproj -c Release --no-restore

# 2) 出包：先删 pck，再 publish（pck 存在时不会重新导出）
if (Test-Path dist\Subaru\Subaru.pck) { Remove-Item dist\Subaru\Subaru.pck -Force }
_tools\dotnet\dotnet.exe publish src\Subaru\Subaru.csproj -c Release --no-restore

# 3) 部署到游戏（游戏必须关闭，否则 WinError 32）
& $py _tools\deploy_mod.py

# 4) 卡牌表
& $py _tools\sync_cardtable.py

# 5) 发布包
& $py _tools\pack_release.py

# 6) 上传工坊（先改 release\workshop\Subaru\workshop.json 的 changeNote）
#    上传器用的是 release\workshop\Subaru\content 里的那三个文件，不是 dist！
#    漏掉这一步会「上传成功但仍发旧版」：日志 PreparingContent 的字节数是旧的。
Copy-Item dist\Subaru\Subaru.dll,dist\Subaru\Subaru.json,dist\Subaru\Subaru.pck `
  -Destination release\workshop\Subaru\content\ -Force
cd release\workshop\Subaru; .\ModUploader.exe upload -w .
```

- **`publish` 经常报 `MSB3073 … 已退出，代码为 -1`**（MegaDot 导出抱怨 editor_settings 保存失败）：只要 `dist\Subaru\Subaru.pck` 时间戳是新的、大小正常就是成功，不用重跑。
- **上传前必须把 dist 的三个文件复制进 `release\workshop\Subaru\content`**（2026-11-19 踩过：0.3.15 第一次上传实际重发了 0.3.14，因为 content 目录还是旧的；Steam 照样回「Successfully uploaded」）。
  验证方法：`check_ws2.py` 的 `file_size` 应该等于 content 三个文件之和（旧的就是旧的）。
- 改了图片资源才需要先 `_tools\megadot\MegaDot_*.exe --headless --path src\Subaru --import`。
- **上传日志里的 `k_EItemUpdateStatusInvalid` 是瞬时状态**，不代表失败。看真实结果用：
  `& $py _tools\tmp\check_ws2.py`（走 `GetPublishedFileDetails`，看 `time_updated` 与 `file_size`）。

## 5. 本轮关键机制备忘

- **先古契约进出牌堆**：`BeforeCombatStart` 用 `CardPile.MoveToBottomInternal` 压底（此时牌堆已在 `SetUpCombat → PopulateCombatState` 铺好）；
  抽完牌在 `AfterPlayerTurnStartLate` 用 `BattleSnapshot.AddCardSafely` 进手；**只改模型不够**，还要 `DeathReturnSpike.RefreshHandUi`（`NPlayerHand` 只在 `PlayerActionsDisabledChanged` / `OnCombatStateChanged` 时重建）。
- **词条只是显示层**：`[保留]` 让位给 `CardModel.get_ShouldRetainThisTurn` 后置补丁（`FlushPlayerHand` 按它分流），`[不可打出]` 让位给 `IsPlayable => false`。
- **瘴气防护四条通道**：`CardCmd.Discard`（单/多）、`CardCmd.DiscardAndDraw`、`CardCmd.Exhaust`、`CardPileCmd.RemoveFromCombat`（单/多）。
  自有卡要动瘴气（契约·贝蒂 / 第一次骑士 / 潘多拉魔女）用 `using (MiasmaGuard.Allow())` 开窗口。
- **致命判定要算上「会救你一命」的效果**：缓冲（`BufferPower`，`AfterOstyLate`，晚一步）与滑溜（`SlipperyPower`，**同相位**）。
  滑溜的例外是「不可被抵挡」伤害（`UnblockablePierce.IsPiercing`），那种照常记死亡。
- **每回合计数器随死归回滚**：对照 `DeathReturnSpike.RewindVersion`（每次成功回档 +1），发现版本变了就清零。
- **`_tools\sync_cardtable.py` 的 `KEYWORDS` 表要和 `SubaruKeywords` 手动同步**：本轮补了 `Contract → 契约`、`WitchCurse → 魔女的诅咒`，
  不补会把关键词列写成空（瘴气那格就被写空过一次）。

## 9. 2026-11-19 下午：CombatSolver（战斗路线求解器）兼容调查 —— 结论是「不需要做」

用户想给 0.3.17 做求解器适配。实测下来发现两件事，都不用我们改代码：

1. **卡死的真凶是奶蛙 mod，不是我们**。求解器 `SolverDisplayNames.CaptureCardTitles` 会
   「一路升级到不能升为止」，奶蛙 `NaiWaWangRi.MaxUpgradeLevel = int.MaxValue` 让它跑约 21 亿次，
   主线程（`SolverDispatcher._Process`）被占死、内存 3.4→11 GB。诊断实证：614 张卡各一次后，
   `NAI_WA_WANG_RI` 重复 9388 次、`SUBARU-` 卡 0 次。完整栈与排查手法见
   `docs/交接_技术问题_2026-11-18.md` §26。
2. **求解器对 Subaru 的既有行为已经是可接受的**：面板正常弹出，显示
   「求解器暂未适配此内容性 Mod：Subaru，无法求解。」，游戏可以正常手打。用户 2026-11-19 明确
   「我认为这个效果可以了」，所以**不做适配层**（真要让它算昴，得按它
   `docs/third-party/README.md` 给 116 张牌逐张写镜像 + publicizer 进内部登记表，工程量不划算）。

已删除的临时文件（都不在 0.3.17 里）：`SubaruCode/Compatibility/SolverCoexistence.cs`
（选昴就关求解器——前提错误）、`SubaruCode/Compatibility/SolverCapabilityDiag.cs`（诊断打点）。
本机 `mods\Subaru\Subaru.dll` 已回到 0.3.17 基线（528,896 字节，hash `DBA40BB5FFA4B1F3…`）。

实用提示：求解器面板占半屏，`Ctrl+F9` 可以隐藏/恢复（它自己的快捷键）。

## 13. 2026-11-19 晚：多人能拿到阵营外卡牌（玩家报）

**根因**：`SubaruCardPool` 里多人分支写成了「除了莎缇拉一律放行」：

```csharp
if (MultiplayerSupport.IsMultiplayer)
    return card is not SatellaWitch;      // ← 把 IsAllowedOnPath 也一起跳过了
```

当初是为了「涅奥恒定给三个契约 → 别出现选了契约却没牌」，结果把**纪元门槛**和**阵营硬切**
一起放宽了：选了贝蒂契约，照样能在奖励/商店/随机生成里刷到帝国军和尸兵的牌。
`IsUnlockedForGeneration` 和 `FilterThroughEpochs` 两处都是这个写法。

**修法**：多人只放宽「解锁门槛」，阵营路线照旧硬切：

```csharp
if (MultiplayerSupport.IsMultiplayer)
{
    if (card is SatellaWitch) return false;
    return AllowedOnCurrentPath(card);    // = card.IsAllowedOnPath(runState)
}
```

新增 `SubaruCardPool.AllowedOnCurrentPath(card)`：非本 mod 的牌直接放行，本 mod 的牌读
`CurrentRunState()` 后走 `IsAllowedOnPath`（路线仍由牌组里的契约牌反推）。

**已知边界**：一个卡池只能对应一条路线。一队里有两个昴且**各自选了不同契约**时，
只有先被 `SubaruRunPath.Current` 扫到的那条生效，另一条线的人会拿不到自己阵营的牌。
这种编队本身和「契约三选一」的设计冲突，暂不处理；要做得更细就得改 `GetPossibleCards`
按 player 过滤（它带 `Player` 参数，但目前没人报这个组合）。

## 14. 2026-11-19 晚：多人首回合「贝蒂阴魔法减费」失效（玩家报）

**排查结论：`BeatricePower` 有两处默认单人环境的假设，在多人里同时出错。**

### ① 回合号哨兵值和「读不到」撞了

```csharp
private int _lastYinTurn = -1;                       // 初值
...
var turn = Owner?.Player?.PlayerCombatState?.TurnNumber ?? -1;   // 读不到也是 -1
return turn != _lastYinTurn;                          // 于是「没打过」= 「打过」
```

多人里 `PlayerCombatState` 在首回合早期可能还拿不到（尚未轮到该玩家初始化），
`turn` 退化成 -1 恰好等于初值 → 首回合判定为「本回合已经打过阴魔法」→ 不给折扣。
之后的回合 `TurnNumber` 读得到，就恢复正常 —— 和玩家描述的「只有第一回合失效」完全吻合。

修：初值改 `int.MinValue`；`turn < 0`（读不到）时**放行**折扣，不再吞掉。

### ② 全场广播的钩子没有判归属

多人里 `Hook` 会把**任何玩家**的出牌、改费广播给所有监听者：

- `AfterCardPlayed`：队友打出阴魔法也会把 `_lastYinTurn` 写成当前回合号
  → 自己的「本回合第一张阴魔法」名额被队友用掉（首回合尤其致命，两边回合号可能相同）
- `TryModifyEnergyCostInCombat`：会去改**队友手里**的阴魔法费用

修：新增 `IsMine(card)`（`card.Owner == Owner.Player`，Owner 为空的按「我的」放行），
两条钩子都先判归属。

### ③ 加了多人专用诊断行

```
[Subaru] mp beatrice: discount <cardId> <cost> -> <newCost> (turn N, last yin turn M)
```

同一 (回合, 牌) 只打一行。玩家复现时把这行发来，就能确认是「没进钩子」还是「判定成打过」。

### 待查（同一类问题，下次做多人时一并看）

`BeatricePower.AfterSideTurnEnd` 里「回合结束自动打出一张临时迷尼亚」没有判
`participants` 里是否有自己 —— 多人里这条 side 级钩子如果对每个玩家回合结束都触发，
贝蒂可能每轮自动打出多张。同类写法在 `BeatriceGuard`（遗物）里已经处理过，这里是遗漏。

## 17. 2026-11-19 晚：一队两个昴、各选不同契约 → 阵营互相顶掉（玩家复现）

**编队**：一个人选「大灾」，一个人选「贝蒂」。大灾那位仍然能在奖励/商店里刷到阴魔法。

### 根因：全局只有一条路线，而卡池出口看不到「在给谁发牌」

`SubaruRunPath.Current(runState)` 遍历 `runState.Players`，**谁先扫到就用谁**并直接返回。
队里有两张契约时必然丢一条：先扫到贝蒂 → 全局路线 = 贝蒂 → 大灾玩家的卡池按贝蒂的规则过滤
（阴魔法放行、尸兵被剔）。这正是 §13 记的「已知边界」，当时判为「暂不处理」。

### IL 实测：纠正一条错误结论（重要）

§13 和 `RewardExclusionPatch` 的老注释都写着「奖励/商店走 `GetPossibleCards`，
它从 `CardPools` 自己拼列表、**不经过** `GetUnlockedCards`」。**这条在 0.113 是错的。**

`_tools\IlDump` 打 `MegaCrit.Sts2.Core.Runs.CardCreationOptions::GetPossibleCards`：

```csharp
IEnumerable<CardModel> GetPossibleCards(Player player)
    => CardPools.SelectMany(pool => pool.GetUnlockedCards(
           player.UnlockState, player.RunState.CardMultiplayerConstraint))
       .Where(c => CardPoolFilter == null || CardPoolFilter(c));
```

也就是说奖励/商店**是**经过池子的（`FilterThroughEpochs` 会生效）。
0.3.20 那次修复对奖励其实是有效的，只是「一条全局路线」把另一半人挡错了。
以前那条「不经过池子」的说法可能是 0.107 的实情，升级后没复核 —— 别再据此做判断。

顺带说明为什么生成专用牌会漏：那是 `IsGenerateOnly` 的自定义过滤没写，跟池子无关。

### 修法：把「路线」分成三种口径，按能不能拿到 player 选

| 口径 | 位置 | 用途 |
|---|---|---|
| `SubaruRunPath.ForPlayer(player)` | 新 | 只看这个人的牌组 → **奖励 / 商店 / 战斗内生成** |
| `SubaruRunPath.All(runState)` | 新 | 队里出现过的全部契约 → 卡池出口取并集 |
| `SubaruRunPath.Current(runState)` | 保留 | 兜底（第一个扫到的） |

对应三处改动：

1. `SubaruCard.IsAllowedOnPath(IRunState)` 拆成「非 virtual 入口 + `virtual IsAllowedOnPath(SubaruPath)`」，
   子类（`CalamityForm` / `UndyingKingBaptism`）改覆写后者 —— 这样按人判定时能带进**指定的**路线，
   而不是让它自己去猜全局路线。
2. `SubaruCardPool`：新增 `internal static AllowedForPlayer(player, card)`；
   `AllowedOnCurrentPath` 改成**并集**（任何一条契约允许就放行）。并集的意义是别把另一半人的牌剔光，
   真正的一刀在 ①的按人判定。
3. `Patches/RewardExclusionPatch`：
   - `CardCreationOptions.GetPossibleCards(Player player)` 后置：补按 `player` 的阵营过滤
     （原来只剔 `IsGenerateOnly`）；
   - 新增 `CardFactory.GetDistinctForCombat` / `GetForCombat` 的 **prefix**：这两个方法带 `player`，
     且在 `TakeRandom` **之前**拿到候选表，所以在 prefix 里把候选剔干净，抽牌时就不会抽到别家的牌，
     也不会出现「本该 3 张只剩 1 张」（后置剔会有这个副作用）。

## 19. 2026-11-19 深夜：0.3.22「程序集初始化失败」+ 三个静默失效的补丁

### 玩家报的症状

「显示模组菜月昴的程序集 DLL 初始化失败」。日志（`godot (4).log`）第 286 行：

```
[ERROR] Exception thrown when calling mod initializer of type Subaru.SubaruCode.MainFile:
 ---> System.Reflection.AmbiguousMatchException: Multiple custom attributes of the same type 'HarmonyLib.HarmonyPatch' found.
   at Subaru.SubaruCode.MainFile.ApplyPatchesIndividually(Harmony harmony, Assembly assembly)
```

### 根因链

1. 0.3.21 里新加的 `CombatCandidatePathPrefix` 在**同一个类**上挂了两个 `[HarmonyPatch]`
   （`GetDistinctForCombat` + `GetForCombat`）—— Harmony 允许，但……
2. `MainFile.ApplyPatchesIndividually` 用的是**单数** `type.GetCustomAttribute<HarmonyPatch>()`，
   一个类有多个就抛 `AmbiguousMatchException`；
3. 这句判断**在 try/catch 外面**（try 只包了 `CreateClassProcessor(...).Patch()`），
   异常直接冒到 `Initialize()` → 整个补丁循环中断 → **中断点之后的补丁全都没挂**，
   连 `[Subaru] patch classes applied=NN` 那行都没打出来（日志里确实没有）。

效果 = mod 半残：时间线/卡牌照常注册（另走一条流程），但大量补丁静默失效。

### 修法（4 处）

| # | 文件 | 改动 |
|---|---|---|
| 1 | `Patches/RewardExclusionPatch` | 拆成 `CombatDistinctCandidatePathPrefix` / `CombatGenericCandidatePathPrefix` 两个类，逻辑放进 `CombatCandidateFilter.Narrow` |
| 2 | `MainFile` | 改用复数 `GetCustomAttributes(typeof(HarmonyPatch), false)`，且**判断挪进 try** → 任何一个类出问题只跳过它自己 |
| 3 | `Patches/NoDiscardPatch` | `NoDiscardAndDrawPatch` 参数名 `cards` → `cardsToDiscard`（游戏里就是这个名字，否则 Harmony 静默跳过） |
| 4 | `Patches/MapMarkerFallbackPatch` | `nameof(CharacterModel.MapMarker)` → `"get_MapMarker"`。属性在 IL 里叫 getter，按属性名找不到方法 —— **这个补丁从 2026-11-18 写出来就一直在被跳过** |

顺带确认兜底资源存在：`SlayTheSpire2.pck`（2049 MB）里有 `map_marker_ironclad`。

### 验证口径（下次遇到同类）

新日志里必须出现 **`[Subaru] patch classes applied=NN, skipped=0`**。
这一行缺席 = 补丁循环没跑完，别只看有没有别的报错。

### 教训

**补丁加载器这类“一个失败带走全部”的结构，会让单点错误表现为“整个 mod 一半功能失灵”。**
判断补丁是否真的挂上，只能认那行 `applied=NN, skipped=0`，不能看功能表现。
