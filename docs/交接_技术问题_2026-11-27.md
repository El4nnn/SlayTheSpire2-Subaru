## 1. 傲慢司教 / 死者之书：卡做完了，但没有任何获取途径

### 现象

玩家反馈这两张牌「从来没在奖励里见过」。查完全部发放入口，确认不是运气问题。

### 根因

两张都是 `CardRarity.Ancient`（先古）。引擎里先古卡**不进普通奖励/商店**，只有两个来源，都在原版硬编码里：

| 来源 | 机制 | 我们的卡 |
|---|---|---|
| 遗物 `ArchaicTooth`（远古之牙，事件 **Orobas** 给） | `TranscendenceUpgrades` 是硬编码六组：`Bash→Break`、`Neutralize→Suppress`、`Unleash→Protector`、`FallingStar→MeteorShower`、`Dualcast→Quadcast`、`FoolishShot→DivineShot`；把牌组里的那张初始牌转化 | ❌ 昴的初始牌（打击/防御/纱幕/基尔提之鞭）一个都不在表里 → `GetTranscendenceStarterCard` 返回 null → 遗物白拿 |
| 遗物 `DustyTome`（尘封之书，事件 **Darv** 给） | 从 `player.Character.CardPool.GetUnlockedCards(...)` 里筛 `Rarity == Ancient && !ArchaicTooth.TranscendenceCards.Contains(c)` 随机取一张 | ⚠️ 唯一可行路径，但我们的池子里还有三张**契约牌**（贝蒂/文森特/斯芬克斯）也是 Ancient，会被一起抽走 |

旁证：`Cards\CreateCards.cs` 的随机稀有池还显式 `RemoveAll(c => c.Rarity != CardRarity.Rare …)`，把先古卡排除在外。

### 定论与处置（0.3.41）

- `Patches\AncientCardSources.cs`：
  - postfix `ArchaicTooth.GetTranscendenceStarterCard`：原版找不到时，牌组里有 `Guiltywhip`（基尔提之鞭）就用它；
  - prefix `ArchaicTooth.GetTranscendenceTransformedCard`：`Guiltywhip` → 新建 `BookOfTheDead`，保留升级与附魔（跳过后面的 vanilla 逻辑，避免兜底成「怀疑」诅咒）；
  - postfix `DustyTome.SetupForPlayer`：抽到三张契约之一就按同一套过滤重抽。
- `ArchbishopPride` 稀有度 `Ancient → Rare`，正常进奖励池；卡面按普通卡比例重裁（500×380 / 736×559，源图 `C:\Users\Elan\Desktop\卡面3\傲慢司教.png` 368×308）。
- **没有**改 `TranscendenceUpgrades` 静态表：`TranscendenceCards`（尘封之书用来排除）读的是同一张表，改表会让昴的死者之书被尘封之书排除，自断一条路。

### 判据

- 用昴在 Orobas 拿「远古之牙」→ 日志 `[Subaru] archaic tooth: CARD.SUBARU-GUILTYWHIP -> BOOK_OF_THE_DEAD`，牌组里基尔提之鞭变成死者之书；
- 在 Darv 拿「尘封之书」→ 日志 `[Subaru] dusty tome: contract filtered, picked …`，抽到的不是契约；
- 图鉴里傲慢司教是**稀有**，卡面为横幅比例。

## 2. 帝国的剑狼：满足条件也解锁不了（计数静默失败）

### 现象

玩家以昴从 A0 打到 A10（至少 10 次通关、30 个首领），「帝国的剑狼」始终不解锁。无报错、无卡死，节点就是不出现。

### 根因（两条叠加）

1. **事件驱动、无回填**。原来只注册 RitsuLib 的 `UnlockEpochAfterBossVictories<Subaru, SwordWolfEpoch>(10)`（`SubaruTimeline.cs:72`）。它只在 `ProgressSaveManager.UpdateAfterCombatWon → CheckFifteenBossesDefeatedEpoch` 那一刻算一次（`BossEpochCompatibilityPatch.Prefix`），错过就永远不补；计数源是 `EncounterStats[id].FightStats` 里按角色 Id 精确匹配的 `Wins` 求和 —— 任何一处对不上，结果恒为 0 且没有日志。
2. **发放只写 `Obtained(4)`**。`BossEpochCompatibilityPatch` 末尾调 `SaveManager.ObtainEpoch`，而原版流程是「获得 → 玩家在时间线界面点一下 → `Revealed(5)`」；`UnlockState` 只收 `State == Revealed(5)`，卡池与解锁判定都只认 5。我们虽然写了 `SubaruEpochGranter.EnsureRevealed()`，但它只由 `EpochMaintenancePatch.TryMaintainEpochs` 调用，而后者唯一调用点是 `PrideFactorSpike.BeforeCombatStart` —— 那件遗物不在场就永远不会补。

对比参照：奶蛙（naiwa）完全不注册 RitsuLib 规则，而是 `NaiWaTimelineProgress.Reconcile()` 挂在**读档后**与**打开时间线时**，自己 `ObtainEpoch/UnlockSlot/RevealEpoch`，还能从 `RunHistory` 回填 —— 所以它「打过的局一定算数」。

### 定论与处置（0.3.41）

新增 `Timeline\SwordWolfProgress.cs`：

- `DerivedWins()`：自己遍历 `ModelDb.Acts` 的 `AllBossEncounters`，在 `Progress.EncounterStats` 里按 `ModelDb.GetId(typeof(Character.Subaru))` 累加 `Wins`；
- 自有计数落盘 `user://subaru_swordwolf.json`（`%APPDATA%\SlayTheSpire2\subaru_swordwolf.json`），**只增不减**；首领战结束若统计没涨，自己 +1（`CombatRoom.RoomType == RoomType.Boss`，来自 `PrideFactorSpike.AfterCombatEnd`）；
- 触发点：读档后（`Patches\SwordWolfReconcilePatch.cs` 挂 `SaveManager.InitProgressData` postfix）、每场战斗开始（`EpochMaintenancePatch`）、每场战斗结束；
- 发放条件：`stored ≥ 10` **或** `MaxAscension ≥ 4`（老玩家补偿：A4 = 至少 4 次通关 ≈ 12 个首领）；
- 发放走 `SaveManager.ObtainEpochOverride(id, EpochState.Revealed)`，一步到位；`SubaruEpochGranter.Grant` 现在遇到「已获得但未揭示」也会补成 Revealed。

### 判据

- 日志：`[Subaru] sword wolf: derived=?, stored=?, required=10, maxAscension=?, bossEncounters=?, characterId=…`；
- `characterId` 必须是 `CHARACTER.SUBARU-SUBARU`（若不同，说明 Id 推导方式要改，这是本机制唯一的剩余风险点）；
- 已满足条件的存档读档后应立即出现 `[Subaru] sword wolf unlocked: …` 与 `[Subaru] epoch upgraded to Revealed: SUBARU_SWORD_WOLF_EPOCH`。
