## 1. `HasCustomAttackVfx` 只停角色动作，通用弹幕照旧飞

**症状（用户原话）**：「我不是让你把默认攻击特效移除了吗」——剑圣那张牌仍然先飞一串昴的子弹，然后才播斩击。

**根因（调用链实证）**

1. `SubaruCard.OnPlay`（`Cards\SubaruCard.cs:494`，`sealed`）里：`:497` 先 `PlayCardAnimation()`，`:509` **无条件**调 `TryPlaySpellVolley(cardPlay)`；
2. `TryPlaySpellVolley`（`:693`）只过滤三件事：牌型不是 `Attack`、目标不是 `AnyEnemy`、以及 `HandlesOwnVolley`（`:699`）——**完全不看 `HasCustomAttackVfx`**；
3. `HasCustomAttackVfx` 当时唯一的消费者是 `PlayCardAnimation`（`:760`），它只负责跳过 `SetAnimationTrigger("Attack"/"Cast")`；
4. `SwordSaintFriend` 是 `CardType.Attack` + `TargetType.AnyEnemy`，正好命中第 2 步的放行条件；
5. 且 `WaitsForVolleyHit` 默认 `true`（`:690`）→ `OnPlay` 在 `:522` 等第一发命中才进 `OnPlayCard`，斩击被整段排到弹幕之后。

所以「专属演出」这个标记只关掉了角色动作，弹幕与命中时序都没管。

**定论**：判定加在弹幕入口（`:705`）——

```csharp
if (HasCustomAttackVfx)
{
    GD.Print("[Subaru] spell volley skipped (custom attack vfx): " + GetType().Name);
    return null;
}
```

**不能**改用 `HandlesOwnVolley => true` 表达：那个标记会让 `AttackSegmentPatch` 整张牌跳过，打击音效与顿帧会一起消失。
标记的分工从此明确：`HasCustomAttackVfx` = 整条默认演出链（动作 + 弹幕），`HasCustomHitSfx` = 每段命中音，`HandlesOwnVolley` = 伤害分段补丁。

**验收日志**：`[Subaru] spell volley skipped (custom attack vfx): SwordSaintFriend`

## 2. 抬手（`Cast`）跟着默认动作一起被停掉

**症状（用户问）**：「那菜月昴抬手的动作还在吗」——剑圣出刀时人站着不动。

**根因**：`HasCustomAttackVfx` 在 `PlayCardAnimation`（`:754`）里 `return` 的位置在 `SetAnimationTrigger` **之前**（`:760-764`），
所以「不播默认攻击动作」和「抬手」被同一个布尔一起关掉了。同一个标记承担了两件事。

**证据**：`subaru.spine-json` 里 `attack` 与 `cast` 是同一段 15 帧（`cast_0000..cast_0013`，两轨完全一致），
第 7 帧（≈0.25s）是抬手定格。

**定论**：抬手挂在 `Vfx.CutIn.Start()`（`Vfx\CutIn.cs:373` 调 `Gesture` → `:306` 发 `SetAnimationTrigger("Cast")`）。
选这里的理由：`Start` 内部前面所有校验（名额、图缺失、容器缺失）失败都会 `return`，
**能发动作就说明立绘一定会出**，不存在「抬手了但立绘没来」的半个节奏。
本回合名额用掉、立绘不出但特效照播时，由 `OnPlay`（`:502-504`）的 `PlayRaiseHand()`（`:736`）兜底。
立绘滑入 250ms ≈ 抬手定格 250ms，两者自然对齐。

**验收日志**：`[Subaru] cutin 'reinhard': gesture (Cast / raise hand)` / `[Subaru] raise hand (no cutin this time): SwordSaintFriend`

## 3. 立绘横向溢出 / 脸出框：高度定标，宽度不可控

**症状**：暴食魔女（横构图棺材）在幕布里左右糊出框外；奥尔巴特的脸贴在右框线上。

**根因（渲染公式）**：立绘是**高度恒等于幕布高度**贴的：

```
p_sc = bh / tex.height          // bh = 幕布高 = 0.98 × 1080 = 1058
渲染宽度 = tex.width × p_sc     = 1058 × W / H
```

`cutin.json` 的 `layers.portrait` **只有 `offsetY`，没有 `dx`** —— 横向位置完全由 PNG 自身的宽高比决定。
所以比例 > 1 的图必然横向溢出（暴食魔女第一版 1349px > 幕布 1113px），比例正常的图则跟着内容偏左/偏右。

**定论**

- 比例控制在 **0.6~0.9**（渲染宽 635~953px，稳落在幕布 1113px 内）；
- 脸偏了**只能改 PNG**：左侧补透明，补白上限
  `P ≤ 1113 × H / 1058 − W`（补到渲染宽 = 幕布宽为止，再多就溢出）；
- **禁止为了「脸居中」去裁右侧**——会把披风/纹章切出直边（用户明确否掉过那一版）；
- 人别顶满幕布（宁可裁到手/髋）；
- **横构图（比例 > 1）的正确修法是上下补透明，不是裁两侧**：补到 `W/H ≤ 1.052`（`_tools\cutin_pad_ratio.py`，
  莫古洛 1024×890 → 1024×975，渲染宽 1110 ≤ 幕布 1113）。裁两侧会把张开的手臂/法杖切掉。

详见 `docs\cutin_工作流.md` §13.3（公式与奥尔巴特实例）与 §13.4（三条构图偏好）。

## 4. 白底抠图：白衬衫被当成背景吃穿

**症状**：剑鬼的纯白衬衫与纯白背景同色（255,255,255），第一版抠完袖子整条消失；白狐立绘的白发/白烟同样风险。

**根因（三条叠加）**

1. **判据**：`min(R,G,B) >= 240` 会把带紫的白衬衫（240,238,246）也算进背景候选；
2. **描边缺口**：角色轮廓的浅灰描边上有几像素断口，边界泛洪从断口漏进衣服内部；
3. **填洞**：为了清掉被围住的白背景而做「填封闭洞」，会把白头发、白烟这些**真正属于角色**的纯白一起吃掉。

**定论**

- 阈值分层：剑鬼 `250`（保住白衬衫）、白狐 `242`（保住白头发/白烟，同时描边仍算背景）；
- 泛洪前先把「非白」掩码**膨胀 3px 封缝**，泛洪后再把背景膨胀回收；
- **不填封闭白洞**（宁可留小块背景，也不吃角色白）；
- 画师签名/绿线这类异物：用「同一行左侧干净区域的颜色」逐行补，不整体改色；
- 棋盘格 JPG（透明区被拍成灰白方格）另走一套判据：中性（max−min ≤ 6）且够亮（min ≥ 225）圈候选，
  封闭小块用「同时含两种灰 + 面积 < 15000px」判定（平涂衬衫是单色，进不了这条）。

**现状**：这四条路都已被 rembg 取代（见第 5 条），脚本保留作离线兜底：
`_tools\cutin_white.py`、`_tools\cutin_chroma.py`、`_tools\cutin_sworddemon_checker.py`。

## 5. rembg 装不上：不是网速，是 pip 的依赖回溯

**症状**：`pip install rembg` 跑 20 分钟，只拉到两个包的 metadata，CPU 烧了 900 秒，一个包都没落地。

**根因**：pip 的**回溯式依赖解析**在 rembg 这条依赖链（onnxruntime / opencv / scipy / numpy 版本交叉约束）上空转；
与网络无关——用户开全局代理后实测 0.4s 响应，换源（清华镜像）也没救。

**定论**：改用 **uv**（`_tools\uv\uv.exe`），同一套依赖 **26 秒**装完。两个后续坑：

| 坑 | 处理 |
|---|---|
| `%LOCALAPPDATA%\uv\cache` 无写权限 | `UV_CACHE_DIR` 指到工作区 |
| `C:\Users\<用户>\.rembg` 建不出来（模型下载失败） | `U2NET_HOME=_tools\rembg\models` |

**结论**：rembg（isnet-anime）对二次元白底/绿幕/棋盘格通吃，边缘无白晕，**优于手写判据**，现在是首选路线
（`_tools\cutin_ai.py`，用户的拖拽入口是根目录 `抠图.bat`）。

## 6. 带 alpha 的图旋转出一圈黑边

**症状**：暴食魔女整具棺材旋转 +10° 摆正后，边缘挂了一圈黑边。

**根因**：抠图后 `alpha = 0` 区域的 **RGB 是垃圾值（通常是 0,0,0）**，而旋转是重采样——
双线性/各向异性会从这些透明像素里取色，与边缘半透明像素混合 → 黑边。

**定论**：旋转**之前**用大半径高斯模糊把 RGB 铺满整张图（只填 `alpha = 0` 的区域），再旋转。

**顺带一条**：这张图的 PCA（主轴分析）失效——棺材两翼面积大于本体，主轴被拉到 59°，转出来是斜的。
多主体/异形构图不要用 PCA 定角，改成**生成候选角度对比图目视挑**
（本轮 ±10/20/30 里 `+10°` 最正，对比图留在 `_assets\cutin\work\_daphne_angles.png`）。

## 7. Python 子进程写不了 D 盘（部署脚本 WinError 5）

**根因：还没查到底。** 现象是「同一路径，PowerShell 可写、Python 子进程不可写，D 盘各目录一致」，

## 8. Harmony 跳过 async 钩子没给 `__result` → 牌悬空、不进弃牌堆

**现象**（用户原话）：「无视格挡的攻击，打在鬼祟珊瑚群身上之后，牌还悬在空中，没有进弃牌堆」
（实际是「强欲司教」那张牌打出去后卡在屏幕上）。

**日志实证**（`godot.log` 17:00 那局）：

```
creator: card added CARD.SUBARU-REGULUS (hand=6)
Player 1 playing card SUBARU-REGULUS (targeting 鬼祟珊瑚群 (index 1))
[ERROR] GameAction PlayCardAction card: CARD.SUBARU-REGULUS ... completed with exception:
        AggregateException → NullReferenceException
  at MegaCrit.Sts2.Core.Hooks.Hook.AfterDamageReceived(PlayerChoiceContext, IRunState, ICombatState,
        Creature, DamageResult, ValueProp, Creature, CardModel)
  at MegaCrit.Sts2.Core.Commands.CreatureCmd.Damage(...)
  at STS2RitsuLib.Combat.AttackHits.AttackHitHook.DamageAndAfterAttackHit(...) line 132
  at AttackCommand.Execute → Subaru.SubaruCode.Cards.Regulus.OnPlayCard (CultistCards.cs:50)
```

**根因（三段，全部有 IL 证据）**

1. `Hook.AfterDamageReceived` 的循环体是 `callvirt AfterDamageReceived` → `callvirt GetAwaiter`，
   中间**没有 null 检查**（`Hook/<AfterDamageReceived>d__29::MoveNext` @008A→@008F）。
2. 我们的 `UnblockableIgnoresHardenedShellPoolPatch`（原 `UnblockablePiercePatch.cs:163`）打的是
   `HardenedShellPower.AfterDamageReceived`，返回值是 **`Task`**（sig 实证），
   而前缀只 `return false` 跳过原方法、**没有声明 `ref Task __result`**
   → Harmony 跳过时返回值取默认值 **`null`** → 引擎对 null 调 `.GetAwaiter()` → NRE
   （所以栈顶就是 `Hook.AfterDamageReceived` 自己这一帧，没有更内层方法）。
3. 触发组合正好是用户说的两件事：**不可被抵挡**（`UnblockablePierce.IsPiercing` 为真才会跳过原方法）
   + 目标带**硬化外壳**（`SkulkingColony.AfterAddedToRoom` 的 IL 里就是
   `Apply<HardenedShellPower>(20)`）。普通攻击 `IsPiercing` 为假 → 走原方法 → 不炸。

**后果链**：NRE → `AttackCommand.Execute()` 任务带异常 → `OnPlayCard` 抛出 →
`PlayCardAction` 以异常结束 → 引擎不再执行「打进弃牌堆」那一步 → 牌停在屏幕上。

> 说明：这一击打出 0 伤害是怪的机制（硬化外壳 20 点额度），与本次崩溃无关。

**定论**：跳过「返回 `Task` 的 async 钩子」时必须给结果。
两处同型缺陷都改了（`ref Task __result` + `__result = Task.CompletedTask`）：

| 补丁 | 目标方法 | 修法 |
|---|---|---|
| `UnblockableIgnoresHardenedShellPoolPatch` | `HardenedShellPower.AfterDamageReceived` | 跳过时 `__result = Task.CompletedTask` |
| `UnblockableIgnoresSlipperyConsumePatch` | `SlipperyPower.AfterDamageReceived` | 同上（滑溜是同一个坑，只是这次没踩到） |

同类里已经做对的是 `MiasmaDoesNotConsumeSlipperyPatch`（`ref Task __result` + `Task.CompletedTask`）——
可以当作范式；全仓 `static bool Prefix` 已扫过一遍，**没有第三处**漏 `__result` 的。

**验收点**：强欲司教打过之后日志里不再有 `completed with exception`，牌正常进弃牌堆；
目标照样不吃硬化外壳（额度不消耗）。

## 9. mod 事件的 `IsAllowed` 被自己的概率补丁绕过（不是昴的局也会出）

**现象**（用户原话）：「我刚才在玩储君时，遇到了爱丽丝与荆棘之王，你确定今天修好了吗」。

**日志实证**（`CHARACTER.REGENT` 那局）：

```
[Subaru] event odds: alice and thorn king 10%
[Subaru] event text panel: EVENT.SUBARU-ALICE_AND_THORN_KING_EVENT ours=True
```

**根因**：0.3.31 给两个 mod 事件加了 `IsAllowed => SubaruEventFlags.PartyHasSubaru(runState)`，
但**那道闸只在引擎 `RoomSet.EnsureNextEventIsValid` 的过滤里生效**；
`Patches\WitchContractChainPatch.cs` 的 `ModEventOddsPatch` 是在 `Hook.ModifyNextEvent` 的 **Postfix**
里直接换 `__result`，判断只有 `runState.VisitedEventIds.Contains(...)`（「本局没走过」），
**没有问 `IsAllowed`** → 塞进去的事件越过过滤，非昴的局照样出。
茶会（15%）是同一个漏洞，只是那次先撞上爱丽丝。

**附带问题**：非昴的局每次抽事件都会白掷一次 `runState.Rng.UpFront.NextFloat()`，等于改动别人的随机流。

**定论**：

1. `CanRollTeaParty` / `CanRollAlice` 里改成 `event.IsAllowed(runState) && !Visited` —— 门槛只留一个来源，
   以后改 `IsAllowed` 不会两头不一致；
2. 两道闸都不过时**先 return、不掷骰**，非昴的局完全不碰 RNG；
3. `WitchContractChainPatch`（茶会→契约）加同样的 `PartyHasSubaru` 兜底。

**验收点**：非昴的局日志里不再出现 `event odds: tea party 15%` / `alice and thorn king 10%`；
昴的局照旧能出。**0.3.33 已发。**

## 10. 选人页「部件全都很大」：背景矩形是 2560×1200，不是 1920×1080

**现象**（用户原话）：「再查一下各个部件的位置，现在还是很大」（截图 2557×1437，2K 屏）。

**证据一 · 引擎设置**（从 `SlayTheSpire2.pck` 里抽出 `project.binary` 解码）：

```
display/window/size/viewport_width  = 1920
display/window/size/viewport_height = 1080
display/window/stretch/mode   = canvas_items
display/window/stretch/aspect = expand
```

**证据二 · 原版背景根节点**（同 pck 里 `scenes/screens/char_select/char_select_bg_regent.tscn`，
`_ironclad.tscn` 同形）：

```
[node name="RegentBg" type="Control"]
anchors_preset = 8                      # 居中
offset_left=-960  offset_top=-521
offset_right=1600 offset_bottom=679     # → 2560×1200
pivot_offset = Vector2(1280, 600)
```

我们自己的日志实测也是 `control=2560x1200` —— 说明引擎把这块矩形原样给了我们的 Control。

**根因**：这块矩形里**真正可见的只有正中 1920×1080**（1K/2K 单位空间相同，只差像素密度）。
我们按 1920×1080 设计、又用 `max()`（cover）拉满 2560×1200 → 整体放大 **1.333 倍**，
并且上下各被切掉 120。这就是「部件全都很大」的唯一原因，不是素材尺寸问题。

**定论**：

1. 背景/视频烘焙成 **2560×1200**（铺满矩形，任何宽高比都不漏边）；
2. 内容（立绘 / 小卡）按 **1920×1080 设计尺寸 1:1** 摆在正中 —— 画布偏移 `(320, 60)`，
   1K 和 2K 屏同一套素材；
3. 脚本缩放改 `min(Size.X/2560, Size.Y/1200)`：控件就是 2560×1200 时 `s=1.000`，
   万一矩形变了也只等比缩小、绝不放大拉变形。

**验收点**：日志出现 `char select bg layout: control=2560x1200 s=1.000 offset=0,0`；
卡片 904×1080、立绘高 1080（此前是 1205×1440 / 高 1440）。

## 11. 选人页音乐「退回主菜单不停」→ 最终定为三个独立循环

**现象**（用户原话）：「点了486，但是直接退回主菜单，音乐不会停」；随后定调
「直接把音乐和视频同步播放不就好了」→ 再改为「视频循环、音乐也循环，三个独立部件」。

```
[Subaru] char select intro started
[Subaru] char select intro finished (holding last frame)
...
[INFO] NGame.Quit called            ← 直到退出整个游戏才出现下一行

```

视频 29.57 s 就播完了，而曲子 4:01、`Loop=true` 一直在循环 → 用户听到的「不停」其实是
**音乐比视频活得久**，不是 `_ExitTree` 没触发（`logs\godot2026-11-22T22.44.32.log` L626/L631/L634/L654
是一轮 `started → stopped → started → stopped`，证明离开页面时 `_ExitTree` 会跑）。

**定论**（按用户最终要求）：

1. 视频 `Loop = true`：29.57 s 自循环；
2. 音乐 `Loop = true`：4:01 自循环；
3. 卡片轮播 4.5 s 换一张 —— **三者各走各的相位，互不打断**；
4. 点角色只重播视频，不动音乐；
5. 离开页面由 `_ExitTree` 统一「停音乐 + 按 `VolumeBgm` 还原原版 BGM 音量」。

**验收点**：日志 `intro started (loop)` + `music started (-14 dB, loop)`；退出时
`music stopped` + `menu bgm restored`。

## 13. 选人页开场「有两处会跳两帧」：一处是素材本身静止，一处是同一帧被放两次

## 14. 「从选人页退回主菜单音乐还在响」：场景没被销毁，`_ExitTree` 抓不到

**现象**（用户原话）：「现在从选角色页面返回主页面还是会播放音乐」。

**日志实证**（`godot.log`，832 行那轮）：`char select music stopped` 只出现在两种时刻——
换角色导致背景场景重建（`music stopped` → 紧接着新的 `char select bg layout`），
以及 `NGame.Quit called` 之后。**返回主菜单没有对应行**。

**根因**：返回主菜单时选人场景并没有被销毁（只是不再显示），所以 `_ExitTree` 不跑、
`StopMusic()` 不执行。此前把 22:44 那轮的 `started→stopped→started→stopped`
误读成「离开即销毁」，实际全是换角色。

**定论**：`_Process` 里加 `WatchLeftScreen()`，两个信号任一成立即停 + 还原 BGM：

1. `!IsVisibleInTree()`（场景被隐藏）—— 必须先「见过自己可见一次」才参与判断，避开进场头两帧；
2. 主菜单重新显示 —— 必须先「见过它隐藏」再看到它显示，避免进场时主菜单还挂着导致误停。

日志会打印停的原因：`char select music stopped (reason=hidden|mainmenu)`。

**验收**：返回主菜单那一刻出现该行 + `menu bgm restored`，主菜单音乐正常。

## 15. 癫狂触发了、手牌瘴气却没被清空：清除被自家防线拦掉

**现象**（用户原话）：「但是为什么手牌中的瘴气没有被销毁」。

**日志实证**（`logs\godot.log` 12:00 那场，就在触发癫狂的同一处）：

```
L1111: [Subaru] madness check: curses=3, pride=3
L1112: [Subaru] miasma remove blocked: CARD.SUBARU-CURSE_WITCH_MIASMA
L1113: [Subaru] miasma remove blocked: CARD.SUBARU-CURSE_WITCH_MIASMA
L1114: [Subaru] miasma remove blocked: CARD.SUBARU-CURSE_WITCH_MIASMA
L1116: [Subaru] madness applied: 3, vulnerable +3
L1117: [Subaru] madness triggered
```

**根因**（拦截方 + 清除方两处）：

1. **拦截方** `SubaruCode\Patches\MiasmaGuard.cs:79-84`：`MiasmaRemoveGuard` 是
   `CardPileCmd.RemoveFromCombat(CardModel, bool)` 的 Prefix，只要 `MiasmaGuard.Allowed`
   没开就 `return false`，并打印 `miasma remove blocked`。
2. **清除方** `SubaruCode\Rewind\Spike.cs:1734`：`TryTriggerMadness` 的清空循环
   **没有开 Allow 窗口**。对照另外三处合法移除全部开了窗口：
   `Cards\BeatriceContract.cs:74`、`Cards\CreateCards.cs:123`、`Cards\KnightCards.cs:113`。

**后果**（比看起来严重）：癫狂加上了、瘴气一张没少 → 计数不清零 → 癫狂 3 回合结束后
下一次判定立刻又是 `curses=3` → 马上二次触发（再叠 3 层易伤）→ **癫狂永不结束、
死归永久失效**，而且每回合继续按手牌瘴气数扣血。

**定论**：清除循环包一层 `using (Patches.MiasmaGuard.Allow()) { ... }`。**0.3.36 已发。**

**验收点**：日志 `madness check: curses=3` → **不应再出现** `miasma remove blocked` →
`madness applied` + `madness triggered`；癫狂结束时手牌瘴气为 0，不会立刻二次触发。

**铁律（新增）**：任何「移除 / 消耗 / 变换」魔女瘴气的代码路径，**必须**开
`Patches.MiasmaGuard.Allow()` 窗口，否则会被防线静默拦掉。
