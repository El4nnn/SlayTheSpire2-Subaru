## 1. 致命伤害落在「回合开始内部」会被漏掉一整轮 ⚠️结构性问题

**症状（玩家原话）**：「本来应该死归的时候没有死归，然后就开始一直死归了」。

**机制**

1. `CapLethalDamage`（`PrideFactorSpike.ModifyHpLostAfterOsty`）把致命压成 `hp-1`、记一次死亡、`_pending = true`；
2. 真正的回档 `RestoreToSavepointAsync` 由 `OnPlayerTurnStart`（挂在 **`AfterPlayerTurnStartLate`**）里的 `if (_pending)` 触发；
3. 如果那一发致命是在**同一段回合开始流程的后半**（`AfterSideTurnStart` 一带：中毒、回合开始的持续伤害）落下的，第 2 步那句判断**已经过了** → 要等**下一个**回合开始才回档。

**日志实证**：`lethal capped (death #1)` 之后整整一个回合（90+ 行）都是出牌/挨打，直到下一个 `greed contract: max energy +1, draw 1`（回合开始）才出现 `resources restored` / `snapshot restored`。

**后果**：① 玩家看到「演出播了但牌堆没回来」；② 他必须带着 1 血打完整个回合，期间每滴伤害都被判致命（日志几十条 `lethal capped again`）；③ 观感变成「一直死归」。

**定论**：在 `PrideFactorSpike.AfterSideTurnStart` 里再补一次 `DeathReturnSpike.FlushPendingRewindAsync`。
- 时机安全：此时回合机已走完玩家回合开始、还没把操作权交给玩家，不在敌方行动链里；
- 不会递归：回档内部重放 `AfterSideTurnStart` 时 `_pending` 已被清掉，直接 return。

**这个结构从 0.1.0 就存在**（28 个发布包逐个 IL 扫过，5 个标记全一致），不是回归 bug，别去翻版本。

## 2. 能量：快照只存当前值，没存上限

**症状**：吃古茶具套装（战斗开始 +2 能量，可超上限）→ 打强欲的契约（上限 +1）→ 死归，显示 **5/4**，应为 **6/4**。

**根因**：`PlayerState.Energy` 存的是 `pcs.Energy`（绝对数），还原时直接覆盖。而上限是动态的：`PlayerCombatState.MaxEnergy` 的 getter 内部会走 `Hook.ModifyMaxEnergy`，跨死归保留的腐蚀能力（强欲的契约）还挂着 → 上限 4，但能量还是「上限 3 时记下的 5」。

**定论**：快照加 `MaxEnergy`，还原用「按上限差平移」：

```csharp
var maxDelta = pcs.MaxEnergy - ps.MaxEnergy;
pcs.Energy = Math.Max(0, ps.Energy + maxDelta);   // 保住超上限那一截
```

## 3. 保留能力的「回合开始效果」不会重跑

**症状**：宫廷小丑死归当回合没有四选一（能力图标在、效果没有）；强欲的契约死归后不抽那 1 张。

**根因**：快照拍在 `AfterPlayerTurnStartLate`，**`AfterPlayerTurnStart` 已经跑完**。玩家在回合中途打出腐蚀能力牌 → 能力被记事本保住、死归后还在，但它的「回合开始」时机早就过去了；我们只重放 `Hook.AfterSideTurnStart`，不重放 `AfterPlayerTurnStart`。

**定论**：`ReplayKeptPowerTurnStartAsync` —— 判据是「**现在身上有、但存档点的能力清单里没有**」（= 死归后新获得且被保留下来的那批），对它们各补跑一次 `AfterPlayerTurnStart`。存档点之前就有的能力绝不能重跑（文森特契约、遗香都在列）。

## 4. 能力计数器藏在 DynamicVars 里

**症状**：旧日雕像（`BygoneEffigy`，进场时给**自己**挂 1 层[缓慢]）死归后缓慢计数不归零，图标继续显示「受伤 +50%」，实际也真的多挨伤害。

**根因（IL）**：`SlowPower.AfterCardPlayed` → `DynamicVars["SlowAmount"] += 1`、`DisplayAmount = SlowAmount × 10`；`AfterSideTurnStart` 清零。快照只存 `Amount` / `AmountOnTurnStart`，**DynamicVars 完全没进快照**。

**定论**：`PowerState.Vars`（`Dictionary<string, decimal>`）存**全部 DynamicVars 的 `BaseValue`**；还原时已存在的能力直接写回，被重建的能力在 `PowerCmd.Apply` 之后再写回。
- 只写 `BaseValue`，不写 `Value`（Value 会叠钩子，写回去等于重复计算）。

## 5. 怪物招式状态机的计数器

**症状**：蜂群术士（`ENTOMANCER`）力量看起来「没重置」。

**IL 实证**：
- Entomancer 身上**没有任何实例字段**（`--fields` 只有两个静态字符串）；力量来自 `SpitMove`：`个人蜂巢 < 3` 时 `Apply<PersonalHivePower>(+1) + Apply<StrengthPower>(+1)`，否则 `Apply<StrengthPower>(+2)`。
- 力量是普通 `StrengthPower`，层数本来就在还原范围内。
- **真正没还原**的是状态机里的两个 bool：
  - `MonsterMoveStateMachine._performedFirstMove`：为真才允许换招（`FindNextMoveState` 里 `if (!_performedFirstMove && _currentState.IsMove) return;`）；
  - `MoveState._performedAtLeastOnce`：配合 `MustPerformOnceBeforeTransitioning` 决定这一招要不要重复（`CanTransitionAway` 就是用它）。

**定论**：两个计数器进快照；还原**必须放在 `ForceCurrentState` / `SetMoveImmediate` 之后** —— `SetCurrentState` 会先跑 `OnExitState()` 把 `_performedAtLeastOnce` 清零，早写等于白写。

## 6. 附魔：只写 `card.Enchantment` 会静默失效

**症状**：死归后有附魔的牌「附魔还在但没效果」。

**根因（IL）**：官方入口 `CardModel.EnchantInternal(enchantment, amount)`：

```
Enchantment = enchantment        // 挂到卡上
Enchantment.ApplyInternal(this, amount):
    Amount = amount
    Card = this                  // ← 反向引用，附魔靠它找自己的卡
```

我们原来只做第一步的等价物（`card.Enchantment = xxx`）→ 反向引用是 null。

**定论**：还原走 `CardCmd.Enchant(st.Enchantment.ToMutable(), card, st.EnchantmentAmount)`；清空走 `CardCmd.ClearEnchantment(card)`；快照里补 `CardExtraState.EnchantmentAmount`。

## 9. 卡面动态变量两个坑（0.3.7 修）

1. **`CalculatedDamageVar` 需要 `ExtraDamageVar`**：用 `IntVar("ExtraDamage", …)` 占名字，`DynamicVarSet.get_ExtraDamage()` 是硬转 → `InvalidCastException` 抛在 `NCard.UpdateVisuals` 里，把整张卡牌奖励界面 `_Ready` 打断（表现：**奖励只有一张卡、不能跳过**）。只有「屏幕上出现这张牌」才触发。
2. **`MakeCalculatedVar(name, baseVal, 乘数函数, mult)` 的 `mult` 是「每单位加成的变量值」**，传 0 → 卡面永远显示 0（阿尔·纱幕的「当前阈值」）。

保留名清单（`DynamicVarSet` 的强类型属性，29 个），撞名就必须用对应类型：
`Block CalculatedBlock CalculatedDamage CalculationBase CalculationExtra Cards Count Damage Dexterity Doom Energy ExtraDamage Forge Gold Heal HitCount HpLoss Item Keys MaxHp OstyDamage Poison Repeat Stars Strength Summon Values Vulnerable Weak`

## 12. 附魔 / 力量 / 卡面（2026-11-18 晚，玩家报「卡面数字没变」「吃不到锋利」）

**引擎的四条附魔通路（IL 实证）**

- Hook.ModifyDamage：先 EnchantDamageAdditive，再 EnchantDamageMultiplicative，取 cardSource.Enchantment
- Hook.ModifyBlock：同样先加后乘，CreatureCmd.GainBlock(creature, BlockVar, cardPlay) 内部读的是 **BaseValue** → 不会重复加成
- CardModel.GetEnchantedReplayCount → EnchantPlayCount（多打次数类附魔）
- 卡面：DamageVar/CalculatedDamageVar/BlockVar/CalculatedBlockVar.UpdateCardPreview 自己会算附魔写进 EnchantedValue，**前提是文案里用 {Damage} / {Block} 占位符**

**两个高频坑**

1. **ValueProp.Unblockable 单独用 = 不是 powered attack**。IsPoweredAttack = HasFlag(Move) && !HasFlag(Unpowered)；
   StrengthPower.ModifyDamageAdditive / VulnerablePower.ModifyDamageMultiplicative / Sharp / Instinct 全都先判它。
   只写 Unblockable（没有 Move）的力量、易伤、锋利、本能、连 Pen Nib/The Boot 都不生效。
   → 一律写 ValueProp.Move | ValueProp.Unblockable，并且 cmd.DamageProps 要显式同步（DamageVar 的 props 不会自动带过去）。
2. **文案里写死数字 = 卡面永远不跟附魔变**。剑圣·莱茵哈鲁特当初写的是「造成 12 ×（X + …）」，12 是纯文本，
   所以附了锋利也不变；改成 {Damage:diff()} 才会显示 15/24。审计脚本：_tools/audit_cardtext.py（写死数字）、_tools/audit_cardvars.py（引用了未声明的变量）。

**结论**：Patches/EnchantPreviewPatch.cs（附魔后补写 EnchantedValue）和引擎自己的算法一致，属于无害兜底；真正的修法是「props 带 Move」+「文案用占位符」。

## 16. 「不可被抵挡」伤害（2026-11-18 晚，原「无视格挡」）

**判定**：`props` 同时带 `Unblockable(2)` + `Move(8)`、且不带 `Unpowered(4)`，并且 `dealer.Side == CombatSide.Player`
—— 见 `Patches/UnblockablePiercePatch.cs` 的 `UnblockablePierce.IsPiercing`。
**敌人打过来的无格挡伤害不吃这套规则**（仍然会被玩家的无实体 / 滑溜 / 硬化外壳挡），
否则等于给怪物的穿透攻击白送一堆收益。
中毒那一跳是 `PoisonPower.Trigger` 传的 `Unblockable|Unpowered = 6`（**没有 Move**），所以**不算**，
否则等于顺手把中毒 Buff 一大截（中毒无视无实体 / 硬化外壳会很离谱）。

**吃（不用写补丁，靠 Move 自然生效）**：力量（`StrengthPower.ModifyDamageAdditive`）、
易伤（`VulnerablePower.ModifyDamageMultiplicative`）、附魔（锋利 / 本能，走 `Hook.ModifyDamage` 的附魔分支）、
本 mod 的增伤（`DamageUpPower` / `WitchFragrancePower` 不查 `IsPoweredAttack`，本来就吃）。

**不吃（8 个 Harmony Prefix）**：

| 效果 | 目标方法 | 短路方式 |
|---|---|---|
| 虚弱 ×0.75 | `WeakPower.ModifyDamageMultiplicative` | 返回 `1` |
| 缩小 | `ShrinkPower.ModifyDamageMultiplicative` | 返回 `1` |
| 无实体（上限压 1） | `IntangiblePower.ModifyDamageCap` | 返回 `-1`（引擎约定 = 无上限） |
| 难以杀灭（上限） | `HardToKillPower.ModifyDamageCap` | 返回 `-1` |
| 滑溜（掉血压到 1） | `SlipperyPower.ModifyHpLostAfterOsty` | 原样返回 `amount` |
| 滑溜（消耗层数） | `SlipperyPower.AfterDamageReceived` | 整个跳过 |
| 硬化外壳（按额度减伤） | `HardenedShellPower.ModifyHpLostBeforeOstyLate` | 原样返回 `amount` |
| 硬化外壳（累计额度） | `HardenedShellPower.AfterDamageReceived` | 整个跳过 |

注意后四个：**只改伤害/血量那一处不够**。滑溜的 `AfterDamageReceived` 会 `Decrement` 层数，
硬化外壳的会把 `result.UnblockedDamage` 累进 `damageReceivedThisTurn`，
只短路 `ModifyHpLost*` 会出现「伤害没被减，但额度被吃掉」的半吊子状态，所以两个钩子都要跳。

文案：三语把「无视格挡 / ignores Block / ブロックを無視する」统一改成「不可被抵挡 / unblockable / ブロックできない」。
只改文案不改行为的老坑见 §12（`Unblockable` 单独用 = 固定伤害，力量易伤全失效）。

## 17. 建筑师对话的 visit 序号（2026-11-18 晚，SUBARU 三段对话）

**引擎怎么挑对话**（IL 实证）：

- `TheArchitect.LoadDialogue`：`charVisits = progress.GetStatsForCharacter(角色).TotalWins`（**之前**通关的次数，本局还没算），
  `totalVisits = progress.Wins`，然后 `GetValidDialogues(角色, charVisits, totalVisits, false)`。
- `AncientDialogueSet.GetValidDialogues` 的筛选条件是**精确相等**：
  `d.VisitIndex.HasValue && d.VisitIndex.Value == charVisits`（`<>c__DisplayClass13_0::b__0`）。
- 匹配不到时走 `AddRepeatingDialogues`：只收 `IsRepeating == true` 且 `VisitIndex <= charVisits` 的段。
- **BaseLib 给模组角色生成的对话从不设置 `IsRepeating`**（`AddAncientDialogues` 的 IL 里没有 `set_IsRepeating`）。
  → 通关次数超过写了几段（我们是 0/1/2 三段）以后，候选列表直接为空。
- 空列表不只是「没台词」：`rng.NextItem(空)` → null → `Dialogue` 为 null →
  `TheArchitect.CreateOptionForCurrentLine` 第一句 `Dialogue.Lines[CurrentLineIndex]` **没有判空** → 空引用，
  直接把登顶流程打断（和 §14 的 `[TODO]` 事故同一类崩法）。

**修法**：`Patches/ArchitectDialogueLoopPatch.cs` 给 `AncientDialogueSet.GetValidDialogues` 挂**后置**补丁，
只在返回空时介入：取该角色最大的 `VisitIndex`，按 `charVisits % (maxVisit + 1)` 重选 → 第 4 次回到第 1 段，之后循环。
返回非空的场合（原版六个角色的重复对话、`FirstVisitEverDialogue`）完全不插手。

**键名格式**（BaseLib `AncientDialogueUtil.GetDialoguesForKey`）：`{表}.talk.{CharKey}` 前缀下，
第 i 段用 `{i}-0r.char` / `{i}-0r.ancient` / `{i}-0r.next` …；另有可选键 `{i}-visit`（int，覆盖段序号）、
`{i}-attack` / `{i}-startattack` / `{i}-endattack`（**值是 `ArchitectAttackers` 枚举名**，写成台词会被 TryParse 丢掉）。
段序号默认 = 段下标（THE_ARCHITECT 前缀）或有映射（其它 ancient）。

自查用日志：`[Subaru] architect dialogue looped: charVisits=N, maxVisit=2 -> visitIndex=X`。

## 18. 先古契约「第一回合开始后进手牌」：模型进了、界面没进（2026-11-18 深夜，玩家报「没生效」）

非[固有]方案（`Cards/AncientContractHand.cs`，挂在初始遗物 `AfterPlayerTurnStartLate`）：
起手正常抽 5 张，抽完之后把契约从抽牌堆直接塞进手牌，手牌 6 张、不占抓牌位。

**日志实证**：`[Subaru] ancient contract moved to hand: 1` 已经打印出来 —— 说明钩子触发了、
`TurnNumber == 1` 判据成立、抽牌堆里也筛到了牌。**牌确实进了 `pcs.Hand`，玩家看到的手牌仍是 5 张。**

**根因**（和死归回档同一类，见 `Spike.cs` `RefreshHandUi` 的注释）：`NPlayerHand` 只在
`PlayerActionsDisabledChanged` / `OnCombatStateChanged` 两个事件里重建；在这条时序里
`CardPileCmd.Add(..., skipVisuals:false)` 没有把新牌并进手牌节点 → 模型 6 张、界面 5 张。

**修法**：塞完牌补一次 `DeathReturnSpike.RefreshHandUi`（与该函数注释里「富足塞一张牌就好了」同理）。
同时把诊断信息打进日志：`moved X/Y, hand=?, draw=?, piles=?` —— 下次直接能区分
「没进模型」（moved 0）和「没进界面」（moved 1）。

**顺带确认的两件事**：

- `PlayerCombatState.TurnNumber` 构造时就是 **1**，只在玩家回合结束切到敌方时 `IncrementTurnNumber`；
  所以第一回合 `AfterPlayerTurnStartLate` 里判 `TurnNumber == 1` 是对的（第 2 回合是 2）。
- 快照抓在塞牌**之前**，所以回档还原后契约仍在抽牌堆，`OnPlayerTurnStart` 跑完会再塞一次，不会重复。
**追加（同日晚）：改成就「压底」而不是「随便在哪」** —— 契约原本只是丢在洗好的抽牌堆里，
有可能正好被起手 5 张抽到，那就白占一个抓牌位。现在 `BeforeCombatStart`（牌堆已铺好、
`StartCombatInternal` 里调 Hook）先把契约 `MoveToBottomInternal` 到抽牌堆最底，
起手 5 张绝不可能碰到它；抽完牌后在 `AfterPlayerTurnStartLate` 再单独塞进手牌。
日志：`[Subaru] ancient contract moved to draw bottom: 1, draw=N`。
快照抓在塞手牌之前、压底之后，所以回档后契约仍在牌堆底，会再塞一次（不会重复、不会进起手）。
极端情况：牌组只剩 5 张（契约 + 4）时起手必然抽到它，此时不再二次塞入，手牌就是 5 张 —— 可接受。
## 19. 死归之后契约「失效」（2026-11-18 深夜，玩家报「契约在死归后失效了」）

**现象**：契约在第一回合正常进手牌；按下「立即死归」后回到存档点，契约躺回了抽牌堆底，手上只有 5 张。

**日志实证**（`godot.log` 23:23 那局）：

```
[Subaru] rewind bonus: +2 str / +1 dex => ...（第 1 次死归）
[Subaru] snapshot restored (no native load)
[Subaru] madness check: curses=1, pride=3
[Subaru] hand ui refresh: side=Player, actionsDisabled=False
```

回档之后**完全没有** `ancient contract moved to hand` —— 塞牌逻辑根本没被调用。

**根因**：塞手牌只挂在初始遗物的 `AfterPlayerTurnStartLate`，那条链只在「回合开始」时跑。
「立即死归」按钮走的是 `RestoreToSavepointAsync`（回合中途直接还原），
还原后牌堆回到「回合开始、抽完牌、契约还压在抽牌堆底」的状态，但没有任何人再把它塞回手上。
自然死亡那条路能自愈（`OnPlayerTurnStart` 里还原完会落到同一个钩子再塞一次），所以只有手动死归会中招。

**修法**：`RestoreToSavepointAsync` 在 `RefreshHandUi(state)` **之前**补一次
`AncientContractHand.MoveIntoHandAsync(ctx, player, refreshHandUi: false)`（界面刷新并进下面那一次，
避免连续两次重建手牌节点）。函数内部自带 `TurnNumber == 1` 判定，所以「迷失」那种更晚的存档点不会误塞；
自然死亡路径上外层钩子再调一次时会因为抽牌堆里已经没有契约而直接返回，不会重复塞。
## 20. 魔女瘴气的全套防护 + 词条合并成【魔女的诅咒】（2026-11-18 深夜）

**现象**：瘴气能被赌徒药水弃掉、能被「消耗」类效果消耗掉。

**为什么原有的 NoDiscardPatch 没挡住**：赌徒药水 / 赌徒筹码 / 精算赌博 / 命运之轮走的是
`CardCmd.DiscardAndDraw(ctx, cards, n)`，不经过 `CardCmd.Discard` 那两个重载（后者其实没人调用，
它们自己也转发到 DiscardAndDraw）。消耗走的是 `CardCmd.Exhaust`（返回 `Task<CardPileAddResult?>`），
移出战斗走 `CardPileCmd.RemoveFromCombat`（契约·贝蒂 / 第一次骑士 / 潘多拉魔女都用它）。

**修法**（`Patches/MiasmaGuard.cs` + `NoDiscardPatch.cs`）：

| 通道 | 拦截点 | 行为 |
| --- | --- | --- |
| 丢弃 | `CardCmd.Discard`（单/多） | 无条件跳过 |
| 丢弃+抽牌 | `CardCmd.DiscardAndDraw` | 剔掉瘴气，抽牌张数改成实际弃掉的张数 |
| 消耗 | `CardCmd.Exhaust` | 跳过，返回 `Task.FromResult<CardPileAddResult?>(null)` |
| 移出战斗 | `CardPileCmd.RemoveFromCombat`（单/多） | 跳过 / 剔除 |
| 保留 | `CardModel.get_ShouldRetainThisTurn` 后置 | 瘴气恒为 true |

**例外窗口**：`MiasmaGuard.Allow()`（`using` 收尾）。明确指名消耗/移除瘴气的自有卡要开窗口 ——
契约·贝蒂、第一次骑士、潘多拉魔女。

**词条合并**：卡面只留【魔女的诅咒】。注意这不是单纯删关键词：
- [保留] 删掉后由 `MiasmaRetainPatch` 直接回答 `ShouldRetainThisTurn`
  （`CombatManager.FlushPlayerHand` 就是按这个属性分流手牌的）；
- [不可打出] 删掉后由 `CurseWitchMiasma.IsPlayable => false` 兜住（`CardModel.CanPlay`
  既查关键词也查 IsPlayable，两条任一条都能拦）。

**自查日志**：`miasma exhaust blocked: …` / `miasma remove blocked: …` / `discard+draw blocked on …`。
若玩家报「瘴气还是被消耗了」，先看这三行有没有出现。
## 21. 致命判定漏算「缓冲」的老问题，同样漏了「滑溜」（2026-11-18 深夜，玩家追问）

**清单里原本只有缓冲有守卫**（§10 最后一条、§16 表格附近）：`CapLethalDamage` 里
`target.Powers` 有未消耗的 `BufferPower` 就放行，不记死亡 —— 因为缓冲挂在
`ModifyHpLostAfterOstyLate`（phase 8），比我们的 cap 晚一步。

**滑溜（`SlipperyPower`）当时没加**，而且它比缓冲更危险：它挂在
`ModifyHpLostAfterOsty`，**和我们这个 cap 同一个相位**，谁先跑取决于模型顺序。
如果遗物先跑，cap 看到的是「原始致命伤害」→ 记一次死亡（`_pending`、遗香 +20、瘴气 +1、
播死归演出）→ 接着滑溜把掉血压到 1，玩家其实活下来 → 变成「明明活下来却被死归」。

**修法**（`Spike.cs` `CapLethalDamage`，紧跟缓冲守卫之后）：

```
if (Patches.UnblockablePierce.IsPiercing(props, dealer))
    // 不可被抵挡：滑溜不生效，照常走致命判定
else
    if (target.Powers 里 SlipperyPower.Amount > 0) → 放行，不记死亡
```

**例外必须保留**：不可被抵挡的伤害本来就绕开滑溜（`Patches/UnblockablePiercePatch.cs` 的
`UnblockableIgnoresSlipperyPatch`），那种伤害是真会打死人的，不能因为身上有滑溜就免疫死归。

**同相位还挂着**：无实体（`IntangiblePower`，但它在 damage 阶段的 `ModifyDamageCap` 已经把伤害压到 1，
到血量阶段已经不可能致命）、钨钢棒（`TungstenRod`，固定 -1，只有「伤害恰好等于当前血量」这一个边界，
目前没加守卫）。

**日志**：`lethal not capped: 滑溜 xN 会压到 1 点 (hp=… amount=… props=… dealer=…)`。

## 22. 事件怎么做：拆「魔女的茶会」+「魔女的契约」（2026-11-19 凌晨，为「爱丽丝与荆棘之王」备料）

**一句话**：事件 = 一个 `CustomEventModel` 子类 + `events.json` 里的几条键。没有池子、没有注册表，BaseLib 扫程序集自动进 `ModelDb.Event<T>()`。

### 22.1 类骨架（`Events/WitchTeaPartyEvent.cs`）

```csharp
public sealed class WitchTeaPartyEvent() : CustomEventModel
{
    // 不写这一行 → Custom 布局：一屏铺满、文字右对齐，和原版事件不是一个样子
    public override EventLayoutType LayoutType => EventLayoutType.Default;

    // 返回 false = 完全不进随机池（契约事件只能被补丁塞进来）
    public override bool IsAllowed(IRunState runState) => !SubaruEventFlags.RefusedTeaParty(runState);

    protected override IReadOnlyList<EventOption> GenerateInitialOptions() => [ ... ];

    public override string CustomInitialPortraitPath => "events/witch_tea_party.png".ImagePath();
}
```

- **类名 → 本地化键**：PascalCase 直接转 UPPER_SNAKE，加 `SUBARU-` 前缀，**`Event` 后缀不删**。
  `WitchTeaPartyEvent` → `SUBARU-WITCH_TEA_PARTY_EVENT`；`WitchContractEvent` → `SUBARU-WITCH_CONTRACT_EVENT`。
  新事件照此：`AliceAndThornKingEvent` → `SUBARU-ALICE_AND_THORN_KING_EVENT`。
- `Id.Entry` 就是这个键，一律用 `{Id.Entry}.pages.…` 拼，不手抄。
- 不覆盖 `Acts` = 共享事件（任何章节都能刷）。
- `Owner` 是 `Player`，`Owner.RunState` 是 `IRunState`，`Owner.Relics` / `Owner.Deck.Cards` 直接可用。

### 22.2 本地化键（`localization/{zhs,eng,jpn}/events.json`）

| 键 | 用途 |
| --- | --- |
| `SUBARU-XXX_EVENT.title` | 事件标题 |
| `…pages.INITIAL.description` | 首页正文 |
| `…pages.INITIAL.options.ACCEPT.title` | 选项按钮主文字 |
| `…pages.INITIAL.options.ACCEPT.description` | 按钮下面那行小字 |
| `…pages.ACCEPT.description` | 选完后的结算页正文 |

正文换行写 json 的 `\n\n`；富文本用 `[gold]…[/gold]`、`[sine]…[/sine]`。

### 22.3 选项与翻页（BaseLib `CustomEventModel`）

- `Option(method, LocString title, LocString description, params IHoverTip[] tips)` —— 茶会/契约用的是这种，键手写。
- `Option(method, string pageKey, tips)` —— 自动推键 `{Entry}.pages.{pageKey}.options.{Slugify(方法名)}`；
  键缺失只在日志里 Warn，界面上就是空按钮，别踩。
- `LockedOption(locKey, pageKey, tips)` —— 无效果/锁定选项。
- 翻页：`SetEventState(PageDescription("ASK"), [ … ])`；`PageDescription("X")` = `L10NLookup("{Entry}.pages.X.description")`。
- 收尾：`SetEventFinished(PageDescription("SIGNED"))`。
- **每一条路径都必须走到 `SetEventFinished`**，否则界面停在那一页，玩家看到的是卡死（茶会源码里的原话）。

### 22.4 给东西的写法（全部在事件里验证过）

给牌（`WitchContractEvent.GrantContract` / 茶会 ACCEPT）：

```csharp
var card = Owner.RunState.CreateCard<GreedContract>(Owner);
var added = await CardPileCmd.Add(card, PileType.Deck, CardPilePosition.Top, null, skipVisuals: true);
CardCmd.PreviewCardPileAdd(added, 0.6f, CardPreviewStyle.EventLayout);
```

- `skipVisuals: true` 必须有：事件界面里没有牌堆节点，等牌堆动画会永远等不完。
  原版 `MuseumOfTorture` 传 false，是因为它自己有展示流程。
- 展示统一用 `PreviewCardPileAdd`，和原版 `CardCmd.AddCurseToDeck` 是同一条路。
- 只从事件获得的牌，卡上加 `IsGenerateOnly => true`，避免进奖励池/商店 —— 强欲的契约就是这么挡的。

给金币：`await PlayerCmd.GainGold(50, Owner);`

给遗物（原版 `MuseumOfTorture` 实证）：`await RelicCmd.Obtain(relic.ToMutable(), Owner, -1);`（-1 = 追加到末尾）

随机药水（原版 `AlchemicalCoffer` 走同一条）：`await PotionCmd.TryToProcure(Owner);`

事件扣血（原版 `SunkenStatue` 实证）：

```csharp
await CreatureCmd.Damage(new BlockingPlayerChoiceContext(), Owner.Creature, n,
    ValueProp.Unblockable | ValueProp.Unpowered, null, null);
```

- `6 = Unblockable(2) | Unpowered(4)`、不带 `Move`：既不吃战斗减伤，也不进「不可被抵挡」规则；
  房间外没有战斗钩子，**不会触发死归**。
- 描述里要显示数值就加 `new HpLossVar(n)`，正文写 `{HpLoss}`（`BookOfTheDead` 同款）。
- **注意**：`PlayerDeathGatePatch` 明确把「非战斗（事件处死）」放行给原版 → 事件扣血是**真会扣死**的。
  现有两个事件都没扣血，所以这一点从没被验证过；设计里的 3/8/13 按 50 血算，低血玩家可能被扣死。

扣生命上限（原版 `MuseumOfTorture` / `TabletOfTruth` 实证）：

```csharp
await CreatureCmd.LoseMaxHp(new BlockingPlayerChoiceContext(), Owner.Creature, amount, null);
```

### 22.5 事件链（`Patches/WitchContractChainPatch.cs`）

- 换下一个事件：`Hook.ModifyNextEvent` 后置，`__result = ModelDb.Event<WitchContractEvent>()`。
  这个点在抽事件之后、`AddVisitedEvent` 之前，所以换掉的事件会正常登记进 `VisitedEventIds`，房间背景也按新事件准备。
- 只改事件不够：`?` 房先掷房型，掷到战斗时 `ModifyNextEvent` 根本不会被调用 ——
  还要后置 `Hook.ModifyUnknownMapPointRoomTypes`，把候选裁成 `{RoomType.Event}`（原集合里没有 Event 就别硬塞）。
- 「本局做过什么」不要另存一套状态：`SubaruEventFlags` 从 `MapPointHistory` 的
  `EventChoices[].Title.LocEntryKey` 里按 `.ACCEPT.` / `.LEAVE.` / `.SIGN.` 片段匹配 —— 事件模型会被复制，
  跨房间状态必须跟存档走，而地图历史本来就写进 `current_run.save`。
- 让事件还能再刷到：引擎按 `VisitedEventIds` 跳过已访问事件，要用反射删 `RunState._visitedEventIds` 里的这条
  （`SubaruEventFlags.AllowEventAgain`）。
- 事件出现率：`ModEventOddsPatch`（原 `TeaPartyOddsPatch`）的做法是「照常随机抽，抽完掷一次换掉」，
  不动 `?` 房本身的事件/战斗分布，被换掉的那次仍会登记进 `VisitedEventIds`。
  2026-11-19 起一次 `NextFloat` 切两个互斥区间：`[0, 0.15)` 茶会、`[0.15, 0.25)` 爱丽丝与荆棘之王。
  别拆成两个补丁各掷一次 —— 后跑的那个概率会被前一个吃掉，且先后取决于 Harmony 顺序。

多张：覆盖 `GetPortraitPath(int screen)`，翻页时 `SetPortrait(int)`（原版 `MuseumOfTorture` 三张）。

### 22.7 落地记录：「爱丽丝与荆棘之王」（2026-11-19）

最终采用的不是早先计划的「四层阶梯」，而是**三个并列选项、各自一页结算**（用户 2026-11-19 给的新文案）：

| 选项 | 结果 | 实现要点 |
| --- | --- | --- |
| 数星星 | 吾星 + 失去 3 点最大生命 | `CreatureCmd.LoseMaxHp(ctx, Owner.Creature, 3, null)` → `RelicCmd.Obtain` |
| 握住他伸出的手 | 荆棘王冠 + 原版诅咒【受伤】 | `RelicCmd.Obtain` → `RunState.CreateCard<Injury>` → `CardPileCmd.Add(skipVisuals:true)` → `PreviewCardPileAdd` |
| 转身离开 | 无 | 只 `SetEventFinished` |

## 23. 遗物栏「有框没图」：NRelic.Reload 被 IsNodeReady 挡掉（2026-11-19，贝蒂的守护）

**现象**：涅奥走「契约·贝蒂」拿到【贝蒂的守护】后，遗物栏里那个位置只有框、没有图标。

**机制**（`sts2.dll` 反查）：

- `NRelic.set_Model` 的实现是 `ModelChanged?.Invoke(...); Reload();`
- `NRelic.Reload()` 第一行是 `if (!IsNodeReady()) return;`
- `NRelic._Ready` **不会**再调一次 `Reload`

所以只要节点是「先设 Model、再挂进场景树」，那一次 `Reload` 就被跳过，而且之后没有任何地方重试，
纹理永远不加载 —— 空框。正常获取走 `RelicCmd.Obtain`，它内部会
`GlobalUi.RelicInventory.AnimateRelic(...)` 播一次「新获得」动画，动画路径会把纹理补上；
而「在事件里直接 `player.AddRelicInternal(...)`」绕过了这条路径，于是中招。

**修法**：`Relics/RelicIconRefresh.cs`（新增）——发完遗物后延迟 0.25s，按 Model 走场景树找到
对应的 `NRelic`，反射调一次 `Reload()`。`NeowContractPatch.GrantBeatriceGuard` 与
`AliceAndThornKingEvent.GrantRelic` 都接上了。

**顺带加的诊断**：发放时会打一行

```text
[Subaru] neow contract: beatrice guard icon res://Subaru/images/relics/beatrice_guard.png exists=True textureNull=False
```

`exists=False` = 路径解析错了；`textureNull=True` = pck 里没有可加载的 ctex；
两者都正常而界面仍然空 = 纯节点刷新问题（现在的 `Reload` 兜底就是治这个的）。

## 24. 从游戏 pck 里抽原版 localization（2026-11-19，做卡牌文案对照用）

想对照原版卡面怎么写，别靠记忆——直接拆游戏包：

- 包：`D:\SteamLibrary\steamapps\common\Slay the Spire 2\SlayTheSpire2.pck`（2.1GB，17369 个文件）
- 格式：`GDPC` + **v3 + `PACK_REL_FILEBASE`**。头部依次是
  `magic(4) / pack_version / ver_major / ver_minor / ver_patch / pack_flags / file_base(u64) / dir_offset(u64)`，
  再 seek 到 `dir_offset` 读 `count`，每条目是
  `path_len(u32) / path(path_len 含结尾 \0) / offset(u64) / size(u64) / md5(16)`，v3 还要多读 `flags(u32)`。
- **两个坑**：
  1. 真实数据偏移 = `file_base + offset`（`file_base` 这里是 112）。不加上就会读到隔壁文件的尾巴，表现是
     解出来的 JSON 开头正常、结尾是另一个语言的文件（比如中文文件里出现德文）。
  2. 目录里记的 `size` **比真实字节数少几个字节**，按 size 截断会让 `json.loads` 报
     `unexpected end of data`。做法：多读 8KB，再 `json.JSONDecoder().raw_decode()` 定界。
- 抽出后就是 `localization/{zhs,eng,jpn}/cards.json` 等，卡牌描述 725 条、卡牌关键词
  `card_keywords.json`、`static_hover_tips.json`（`FATAL`=斩杀、`STUN`=击晕）都在里面。
- 脚本：`_tools/tmp/extract_vanilla_loc3.py`（抽取）、`_tools/tmp/cmp_style.py`（统计对照）、
  `_tools/tmp/mod_flags.py`（扫 mod 文案偏离）。产物在 `_tools/tmp/vanilla/`。
- 顺带确认的官方用词：`晕眩` 是状态牌「晕眩」的名字，**让敌人停一回合叫「击晕」**；
  `斩杀`（FATAL）是「击杀时触发」的词条，不是动词；`缩小`(SHRINK)、`不可格挡`(NO_BLOCK) 都是官方能力名。
## 25. 「帝国的剑狼」永远不解锁：RitsuLib 只接管「它认识的角色」（2026-11-19，玩家反馈）

**症状**：玩家已经通关多次、打到进阶 4，剑狼节点一直不出现。

**链路（`sts2.dll` / RitsuLib 0.113 的 IL 取证）**：

1. `ProgressSaveManager.UpdateAfterCombatWon`
   → `GetOrCreateEncounterStats(...).FightStats.IncrementWin(...)`（先把这场胜场记进 EncounterStats）
   → `if (room.RoomType == Boss) CheckFifteenBossesDefeatedEpoch(this, player)`；精英走
   `CheckFifteenElitesDefeatedEpoch`，阈值都是 15。
2. 原版这两个方法内部是一串 `isinst Ironclad / Silent / Regent / Defect / Necrobinder / Deprived / Fool`，
   **摸不到就 `throw new ArgumentOutOfRangeException("character")`**。
   计数 = `Progress.EncounterStats` 里 BOSS 遭遇的该角色 `Wins` 求和，`>= 15` 才 `TryObtainEpochMidRun`。
3. RitsuLib 的 `BossEpochCompatibilityPatch.Prefix` 第一句是
   `if (!ModCharacterTimelinePolicy.IsOwnedOrUsesTimelinePolicy(character)) return true;` —— 放行原版。
4. `IsOwnedOrUsesTimelinePolicy` = `ModContentRegistry.TryGetOwnerModId(角色运行时类型)`
   **或** 角色实现 `STS2RitsuLib.Scaffolding.Characters.IModCharacterEpochTimelineRequirement`。
5. 我们：`Subaru : PlaceholderCharacterModel`（BaseLib 的角色），
   `ModContentPackBuilder.For("Subaru")` 只交了 Story / Epoch / 解锁规则，**从来没注册角色本身**，
   角色也没实现那个接口 → 第 3 步放行 → 第 2 步抛异常。

**后果**：每次用昴打掉 BOSS 或精英，局后结算里都抛一次异常，`CheckFifteenBossesDefeatedEpoch`
（以及 RitsuLib 替它跑的 10 次规则）**从来没执行过**，剑狼自然永远不发。
EncounterStats 的自增发生在抛之前，所以统计数字看着是对的、只有解锁不生效，很容易误判成「阈值太高」。

**为什么别的节点能解锁**：那些走 RitsuLib 的**局后角色解锁补丁 + 模板推导**
（`PostRunCharacterUnlockEpochCompatibilityPatch`），不走这套 ownership 判定；
只有「15 首领 / 15 精英」需要。

**修法（2026-11-19 已改）**：

1. `Character/Subaru.cs`：`public class Subaru : PlaceholderCharacterModel, IModCharacterEpochTimelineRequirement`
   + `public bool RequiresEpochAndTimeline => true;`。
   启动时会有一条 `[Content] Unregistered character uses RitsuLib timeline policy: …` 的 warn，属正常。
2. `Timeline/SubaruEpochGate.cs`：剑狼前置从 `SUBARU_WITCH_END_EPOCH` 改成 `SUBARU_EPOCH_CALL`。
   原来「10 个首领」和「必须先通关」两条不同步，会出现「局后发放 → 下一场战斗开始被
   `EnforceChains` 当缺前置删掉」的闪烁。
3. 诊断：每局第一次战斗开始时打一行
   `[Subaru] timeline policy: character=CHARACTER.SUBARU-SUBARU policy=True`。

**验证**：更新后再打一个 BOSS，日志里应出现
`[Unlocks] Obtained epoch 'SUBARU_SWORD_WOLF_EPOCH' after N boss win(s) using registered rule: …`；
若出现 `… has no registered boss-win epoch rule …`，说明规则注册没生效（跟计数无关）。

**给别的模组作者的提醒**：只做 BaseLib 角色 + RitsuLib 时间线，一定会踩这个坑；
要么实现 `IModCharacterEpochTimelineRequirement`，要么把角色交给 RitsuLib 的 content pack 注册。

**工具**：`_tools/tmp/ildump/` 是这次自己写的 IL 反汇编器
（`System.Reflection.Metadata` + `System.Reflection.Emit.OpCodes` 表，token 解析成可读名字）。
用法：`dotnet ildump.dll <assembly> <TypeName 可带*> [MethodName]`。
注意 `OpCodes` 的两字节 opcode 要按 `(ushort)Value` 建表，否则 0xFE 开头的一律解不出来。


## 26. 装了「战斗路线求解器」(CombatSolver) 后进战斗必卡死（2026-11-19，查出真凶是奶蛙 mod）

**症状**：订阅 CombatSolver 0.51.8 后，进第一场战斗 1～2 秒内整窗无响应，`godot.log` 永远停在
`[Subaru] hand ui refreshed`；Windows 事件日志记 `AppHangTransient`（12:48、13:04 两次）。

**工具**：`dotnet-stack report` 连不上目标进程——沙箱禁止命名管道，`UnauthorizedAccessException:
Access to the path is denied` at `NamedPipeClientStream.TryConnect`。改走 Win32：
`MiniDumpWriteDump(pid, file, 0 /*MiniDumpNormal*/)` 拿 1.6 MB 的 minidump（写 dmp 的 PowerShell
里别用 `$pid` 当变量名，它是只读自动变量，会静默 dump 了 PowerShell 自己），再
`dotnet-dump analyze <dmp> -c "clrstack -a -all"` 读托管栈。

**主线程栈**（从下往上看）：

```
CombatSolver.SolverDispatcher._Process(delta)                       ← 每帧，Godot 主线程
  CombatSolver.SolverController.MonitorCombatPresence()
    CombatSolver.SolverController.RequestSearch(NGame, CombatState, ...)
      CombatSolver.SolverDisplayNames.Capture(combatState)
        CombatSolver.SolverDisplayNames.CanonicalCardNames()
          CombatSolver.SolverDisplayNames.CaptureCardTitles(...)    ← 逐张卡
            RitsuLib.SecondaryResourceUpgradePreviewCosts.Capture(card)
              RitsuLib.SecondaryResourcePaymentResolver.SnapshotUses(card)
                RitsuLib.PaymentResolver.GetCapabilityUses(card)     ← List.AddRange
                  RitsuLib.ModelCapabilityHost.GetCapabilities<T>()
                    RitsuLib.ModelCapabilityDefaults.GetModifiers(type)
```

线程是**在跑**不是在等：3 秒消耗 2.41 s CPU（≈单核 80%），内存 3.4GB → 11GB。RitsuLib 那几个
方法静态读 IL 全是有限数组迭代，不可能是循环点 —— 所以做了临时诊断（**已删**）给
`SecondaryResourceUpgradePreviewCosts.Capture` 挂 prefix/finalizer 写
`%APPDATA%\SlayTheSpire2\subaru_solver_diag.txt`。

**诊断结果**（1MB / 20003 行）：614 张卡各处理 1 次，然后 `CARD.NAI_WA_WANG_RI` 处理了 **9388 次**
（撞到 2 万行上限），`SUBARU-` 开头的卡 **0 张** —— 还没轮到我们就已经打转了。

**真因（两段代码相撞）**：

1. `CombatSolver.SolverDisplayNames.CaptureCardTitles` 是个「升级到不能升为止」的循环：
   `names[(Id.Entry, CurrentUpgradeLevel)] = Title` → `if (!card.IsUpgradable) return` →
   `UpgradeInternal()` + `FinalizeUpgradeInternal()` → 跳回循环。每次 key 里的等级不同，字典无限变大。
2. 奶蛙 `lib\beta\naiwa.dll`：`NaiWa.cards.NaiWaWangRi::get_MaxUpgradeLevel` 直接返回
   `ldc.i4 2147483647`（int.MaxValue），`IsUpgradable` 永远为真 → 循环约 21 亿次。

而且 `CanonicalCardNames()` 枚举的是**所有 mod 的 canonical 卡表**，与角色无关 ——
所以这不是「昴专属」，用任何角色开一局都会卡。

**结论 / 处置**：

- 与 Subaru 无关。已反馈给两个作者；用户取消奶蛙订阅后卡死消失。
- 当时的临时方案「选昴就关求解器」前提是错的，**已删除**（`Compatibility/SolverCoexistence.cs`），
  连同诊断补丁（`Compatibility/SolverCapabilityDiag.cs`）。mod 回到 0.3.17 基线（dll 528,896）。
- CombatSolver 对 Subaru 的最终表现是**优雅拒绝**：面板照常弹出，显示
  「求解器暂未适配此内容性 Mod：Subaru，无法求解。」，游戏可以正常手打。用户认可这个结果，
  因此**不做第三方适配层**（要真让它算昴，需要按它 `docs/third-party/README.md` 给 116 张牌
  逐张写镜像，工程量极大且要 publicizer 进内部登记表）。

**两条可复用教训**：

1. `_Process` 里做重活的第三方 mod（求解器、UI 增强）会把**任何**「无限升级 / 无限生成」的
   第三方内容放大成主线程死循环。以后遇到「装某个 mod 就卡死」，先抓主线程托管栈，别猜。
2. `Entry.Enabled` 这类总开关不一定管得住一切：CombatSolver 的 `_Process` IL 里
   `MonitorCombatPresence()` 在 `get_Enabled` **之前**调用（`@008B` vs `@0095`），
   关掉 Enabled 只挡后面的 `Dispatcher`。要真关，得挂 `MonitorCombatPresence` 自己。
